# tailchat для Android

Нативный клиент того же чата: тот же протокол, тот же порт, тот же рандеву —
но экран телефона вместо терминала. Разговаривает с обычным `tailchat` на
компьютере без каких-либо настроек на стороне компьютера.

## Что нужно на телефоне

- Android 10 (API 29) или новее.
- Установленное и **подключённое** приложение Tailscale. Оно поднимает VPN, и
  весь трафик к адресам `100.64.0.0/10` идёт через него — приложению tailchat
  для этого ничего делать не надо.
- Разрешение на уведомления (спрашивается при первом запуске). Без него чат
  работает, но о сообщении в фоне никто не скажет.

Приложение **не** требует ни `tailscale` CLI, ни Termux, ни root.

## Установка

Готовый APK: `app/build/outputs/apk/release/app-release.apk` (~3.4 МБ).
Скопируйте на телефон и откройте — Android спросит разрешение на установку из
этого источника. Подпись самодельная (`tailchat-release.jks` в этой папке), так
что обновлять поверх можно только APK, собранными тем же ключом.

Проще всего — ссылка «Android APK» в веб-версии
(<https://repentandliveholy.org/tailchat/>): она отдаёт **этот** APK.

## Публикация APK для веб-версии

`/tailchat/tailchat.apk` — единственная ссылка на скачивание в веб-клиенте
(экран входа и лист настроек). С 0.54.0 там лежит **этот нативный APK**, а не
обёртка из `../android-twa`: обёртка была временной мерой, пока нативного
клиента не было. Файл не в git (`.gitignore`: `web/cloud/tailchat.apk`) —
бинарник каждой сборки в истории репозитория никому не нужен, — а на сервере
это host-only файл, который `bin/production-deploy.js` намеренно сохраняет
между деплоями. Значит, обновляется он отдельно от кода:

Одной командой из корня репозитория — и так на **каждом** релизе:

```bash
node bin/release-android.js
```

Она собирает release, кладёт APK локально (`web/cloud/tailchat.apk`, для
`bin/cloud-server.js`), загружает на сервер через временное имя (чтобы никто не
скачал половину файла), **скачивает опубликованный URL обратно и сверяет
sha256** — именно этой проверки не хватало, когда ссылка месяцами отдавала
старую обёртку, — и отправляет APK в Telegram, если настроены
`TAILCHAT_DEPLOY_TG_TOKEN`/`TAILCHAT_DEPLOY_TG_CHAT` (`.env`, см.
`.env.example`). Версия читается из `app/build.gradle.kts`, так что подпись
сообщения не может разойтись со сборкой. Ключи: `--no-telegram`,
`--host <ssh-alias>`.

Вручную то же самое:

```bash
cd android && ./gradlew assembleRelease
cp app/build/outputs/apk/release/app-release.apk ../web/cloud/tailchat.apk   # локальный сервер
scp app/build/outputs/apk/release/app-release.apk ovh:/opt/tailchat/web/cloud/tailchat.apk
```

Проверка — не «файл скопировался», а «отдаётся именно он»:

```bash
curl -sD- -o /tmp/served.apk https://repentandliveholy.org/tailchat/tailchat.apk | head -1
shasum -a 256 /tmp/served.apk android/app/build/outputs/apk/release/app-release.apk   # суммы должны совпасть
$ANDROID_HOME/build-tools/*/aapt2 dump badging /tmp/served.apk | head -1                # net.tailchat.android, нужный versionCode
```

Пакет нативного клиента (`net.tailchat.android`) не совпадает с пакетом обёртки
(`org.repentandliveholy.tailchat`), поэтому у тех, кто успел поставить обёртку,
нативный APK встанет **рядом**, а не поверх: старое приложение надо удалить
руками. Ключ подписи тоже другой — обновлять нативный APK можно только APK,
подписанным `android/tailchat-release.jks`.

## Настройка

Одно поле: **peer** — машина, с которой вы говорите. Принимает MagicDNS-имя
(`desktop-example`), полное имя (`desktop-example.mynet.ts.net`) или адрес
`100.x.y.z`. Порт по умолчанию 4747 — тот же, что у консольного клиента.

На компьютере запускается обычный `tailchat` с tailnet-именем телефона:

```bash
tailchat <имя-телефона-в-tailnet> --name Roman
```

Кто из двоих запустится первым — не важно: рандеву симметричный, оба слушают и
оба звонят, побеждает один канал.

## Что умеет

- Сообщения в обе стороны, с расписками: `·` в очереди, `✓` доставлено,
  `✓✓` прочитано. `✓✓` уходит только когда чат действительно на экране — как и
  в консольном клиенте, «прочитано» означает, что человек мог это увидеть.
- Индикатор набора и присутствие (`active` / `idle` / `away`).
- Офлайн-очередь: написанное без связи уходит по порядку, когда связь появится.
- Кеш переписки на устройстве (тумблер «Кеш переписки» в настройках, по
  умолчанию включён): как только приходит ростер, клиент в фоне догружает
  историю всех диалогов, где её ещё нет (сначала непрочитанные, затем по
  свежести), максимум двумя запросами одновременно, никогда не перебивая
  открытый чат, — поэтому диалог открывается мгновенно и читается без сети;
  выключение тумблера останавливает догрузку и очищает уже загруженное.
- Файлы в обе стороны, с проверкой sha256. Принятое кладётся в общую папку
  загрузок — `Download/tailchat/` — а не в приватный каталог приложения, иначе
  файл «пришёл», но его нельзя открыть ничем. Нажатие на принятый файл открывает
  «Загрузки».
- `/wake` с компьютера поднимает отдельное уведомление с вибрацией.
- Уведомления о сообщениях, когда приложение в фоне; постоянное уведомление
  показывает состояние канала.
- История переписки на устройстве (`transcript.ndjson`, по одному JSON на
  строку), выключается тумблером в настройках.
- Список устройств собеседника, если он их присылает: можно перевести разговор
  на другую его машину одним нажатием.

Чего нет по сравнению с консольным клиентом: ИИ-собеседник, ASCII-графика,
подсветка кода, разметка сообщений — всё это про терминал.

## Cloud-ядро

Нативное приложение работает прежде всего как cloud-клиент существующего
backend. Прямой P2P/Tailscale-режим сохранён через `proto/` без изменений и
открывается отдельной кнопкой как дополнительный режим.

Cloud-экран является стартовым экраном приложения. Реализовано:

- выбор cloud-сервера; по умолчанию `https://repentandliveholy.org`;
- регистрация через `POST /tailchat/api/register`;
- вход через `POST /tailchat/api/login`;
- тот же JSON-контракт, что у web/terminal клиентов, включая `pubKey: null`;
- отображение одноразового recovery key после регистрации;
- приватное хранение адреса сервера, токена, логина и имени в
  `SharedPreferences` приложения (`cloud-session`);
- подключение к `/tailchat/ws`, auth/ready handshake и живой roster с
  online/pending-состоянием;
- выбор диалога через `{k:"subscribe",peer}` и ожидание серверного
  `{k:"subscribed"}` перед отправкой;
- загрузка истории через `GET /tailchat/api/history?peer=...`;
- отправка и приём текстовых `{k:"frame"}`, оптимистичный локальный показ и
  дедупликация серверного self-echo по `id`;
- Saved messages — диалог пользователя с самим собой;
- повторное подключение и локальный выход из аккаунта;
- автопереподключение cloud-сокета: экспоненциальная задержка 1–30 с (тот же
  график, что у `Rendezvous.kt` и у `src/cloud/link.js`), сброс задержки при
  успешном соединении, мгновенный повтор при возврате сети
  (`ConnectivityManager.NetworkCallback`) и при возврате приложения на
  передний план, плюс ручная кнопка «Подключиться снова» в шапке ростера,
  когда канал офлайн;
- ack/read-расписки для входящих и исходящих сообщений, с отображением в
  переписке (`·` в очереди, `✓` доставлено, `✓✓` прочитано — тот же язык, что
  у P2P-режима и у терминального клиента), `k:"unread"` →
  счётчик и preview непрочитанного в ростере;
- добавление друзей по одноразовому коду (`POST /invite`,
  `POST /invite/accept`) — кнопкой в нижней панели ростера или командой `/invite`;
- терминальные команды в композере cloud-диалога: `/help /clear /theme
  /ping /wake /notify /sound /typing /nick /happy /sad /neutral /time
  /history /peer /invite /logo /quit` — системные заметки в диалоге,
  ping/pong с RTT, typing-индикатор, экспорт переписки в
  `Download/tailchat/*.txt`;
- файлы через живой relay-протокол `file-offer`/`file-chunk`/`file-done`/
  `file-deny` (`net.tailchat.proto.FileTransfer`, тот же порт, что и у
  P2P-режима: `CHUNK_BYTES`, `DEFAULT_MAX_BYTES` 100 МБ — как `FILE_MAX_BYTES`
  в `web/cloud/app.js`, sha256-проверка, потоковая передача в обе стороны
  (отправка читает документ порциями, приём пишет во временный файл в
  `cacheDir`, целиком в память файл не попадает), сохранение в
  `Download/tailchat/`) — требует, чтобы собеседник был
  сейчас в сети, так как эти кадры не ставятся в офлайн-очередь
  (`QUEUEABLE` в `src/cloud/hub.js` содержит только `msg`/`ai`/`ack`/`read`);
- фото — сжимаются на устройстве (длинная сторона 800px, JPEG q75, с учётом
  EXIF-поворота) и уходят как `image: {dataUrl,width,height}` внутри
  обычного `msg`-кадра, поэтому, в отличие от файлов, ставятся в очередь и
  остаются в истории так же, как текст;
- голосовые сообщения — запись через `MediaRecorder` (AAC/M4A, 16 кГц моно,
  24 кбит/с, до 10 минут — те же лимиты, что и `VOICE_MAX_SEC`/битрейт в
  web/cloud/app.js, и тот же клампинг, что и серверный `normalizeMedia`),
  отправляются как `voice: {dataUrl,duration}` в
  `msg`-кадре, тем же путём очереди и истории, что и фото; воспроизведение
  через `VoicePlaybackController` (один `MediaPlayer` на открытую беседу) с
  waveform-плеером внутри пузыря;
- пять тем (`Settings.appTheme`): системная, светлая, тёмная, Ocean,
  Amber — с синхронизацией цвета системного статус-бара и `Crossfade`
  между палитрами; переключаются из шторки настроек или командой
  `/theme`;
- синтезированные звуковые сигналы (`SoundEffects`, `ToneGenerator`, без
  аудио-файлов) на отправку/приём сообщения и `/wake`, с переключателями
  звука/уведомлений/вибрации/typing-статуса в настройках;
- визуальный язык ближе к терминальному клиенту, а не общий Material:
  расписки используют тот же трёхуровневый набор глифов, что и
  `MARKER_RANK`/`MARKER_COLOR` в `src/ui.js` (`⧗` в очереди — янтарный,
  `✓` отправлено, `✓✓` прочитано — вместо произвольной точки); присутствие
  собеседника показывается тем же `●`/`○`, что и в `picker.js`; `/help` и
  `/peer` оформлены как секции терминального клиента (`── label ──────`,
  `ui.js`'s `addSection()`); поле ввода несёт тот же каретка-промпт `❯`,
  что и `ui.js`'s `prompt`-бокс — как ведущая иконка на обычном скруглённом
  поле, а не полная имитация blessed-рамки;
- явные `:shortcode:`-эмодзи (`:good: :bad: :love: :ok: :please: :smile:
  :cry: :laugh: :yes: :no:`) заменяются на отправке — тот же словарь и та
  же безусловная (не завязанная на настройку) половина `src/emoji.js`
  (`COLON_EMOJIS`/`replaceColonEmojis`); словесная авто-замена
  (`EMOJI_DICT`, переключатель `autoEmoji`) не портирована;
- тело сообщения классифицируется целиком, тем же способом, что и
  `appendMessage()` в web/cloud/app.js: если оно целиком обёрнуто тройным
  бэктиком — моноширинный блок кода; если целиком начинается с `"> "` —
  цитата с левой чертой (остаток текста, включая внутренние переводы
  строк, идёт как есть, без ссылок — как и в web); иначе — обычный текст,
  где `http(s)://`-ссылки кликабельны (`formatTextWithLinks()` в
  web/cloud/app.js, `LinkAnnotation.Url` на Android). Разбор построчно, а
  не по всему сообщению, был реализован и отброшен: одно и то же
  сообщение рендерилось бы иначе на Android, чем на web/term — языковая
  подсветка `src/highlight.js` остаётся terminal-only.

Основные файлы:

| Файл | Назначение |
|---|---|
| `cloud/CloudApi.kt` | REST: auth, история (включая `image`/`voice`), invite create/accept |
| `cloud/CloudSocket.kt` | WebSocket auth, roster, presence, subscribe и frames (msg/ack/read/unread/wake/typing/ping/pong/file-offer/file-chunk/file-done/file-deny) |
| `cloud/CloudSessionStore.kt` | локальная cloud-сессия |
| `cloud/CloudController.kt` | сессия, roster, история, команды композера, ping/typing state, файлы, фото, голосовые |
| `ui/CloudScreen.kt` | авторизация, ростер, переписка, вложения, фото-вьюер, голосовой плеер, системные заметки |
| `ui/CloudSettingsSheet.kt` | тема, звуки, уведомления, вибрация, приглашение друга |
| `SoundEffects.kt` | синтезированные тоны событий |

Foreground service владеет одновременно прежним `ChatEngine` и новым
`ServiceCloudController`, поэтому cloud-сокет не принадлежит Activity и не
пересоздаётся вместе с экраном.

Обычная release-сборка сохраняет системный запрет cleartext HTTP: пароль и
токен нельзя случайно отправить без TLS. Только
`app/src/debug/AndroidManifest.xml` разрешает HTTP, чтобы эмулятор мог
подключаться к изолированному серверу на машине разработчика.

Уведомления и переподключение работают, пока foreground service жив —
`ChatService` пережидает закрытие экрана и уход приложения из недавних (это
весь смысл foreground-канала), а автопереподключение выше означает, что
сокет не просто ждёт, когда его переоткроют вручную, а сам восстанавливает
канал при разрыве, смене сети или возврате в приложение. Приложение один раз
просит освобождение от батарейной оптимизации
(`REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`), чтобы агрессивные OEM-менеджеры
батареи не убивали канал через несколько часов простоя. Голосовые сообщения
записываются через `MediaRecorder`, вызываемый из `ServiceCloudController` —
то есть из процесса `ChatService`, а не Activity, поэтому манифест
объявляет `RECORD_AUDIO` и `FOREGROUND_SERVICE_MICROPHONE`, а тип
foreground-сервиса — `specialUse|microphone`: с Android 14 без этого доступ
к микрофону из работающего foreground-сервиса запрещён вне зависимости от
того, что запись инициировал видимый экран. `BootReceiver`
перезапускает `ChatService` после ребута или обновления приложения, если
есть сохранённая cloud-сессия или настроенный P2P-пир — без этого канал
оставался мёртвым до ручного открытия приложения, а автопереподключению
нечего было переподключать: процесса ещё не существовало.

Это всё ещё не «настоящий» push уровня ОС (FCM/UnifiedPush) — процесс
должен быть жив, чтобы держать сокет, и полностью выгруженное состояние
`BootReceiver` покрывает только при следующем ребуте, а не мгновенно.
Сервер уже умеет self-hosted Web Push (`src/cloud/push.js`, VAPID) для
web-клиента, и `POST /tailchat/api/push/subscribe` протокольно принял бы и
Android-подписку через UnifiedPush без изменений на сервере — но это
требует диспетчер-приложение на телефоне (например ntfy) и реализацию
расшифровки Web Push (RFC 8291) на Android, отдельная задача, не сделана.
В пределах живого процесса доставка больше не зависит от ручного
переоткрытия приложения. Пока не реализовано редактирование профиля
(аватар/имя меняются только через `/nick` и локальную сессию, без REST
для смены отображаемого имени).
Команды `/ai`, `/asc`, `/holiday`, `/saver` веб-клиента не портированы —
либо требуют AI-моста, либо не имеют осмысленного мобильного эквивалента.
Не портированы: опциональный WebRTC-апгрейд cloud-диалога до прямого
data-channel «на лету» (web/cloud/app.js's `directLinks`/`rtc-*` —
P2P на Android уже есть, но отдельным экраном, а не upgrade текущего
cloud-диалога — нужна отдельная зависимость на `org.webrtc` и сигналинг
через `CloudSocket`), словесная авто-замена эмодзи без двоеточий
(`autoEmoji`), голосовая amplitude-визуализация при записи/воспроизведении
и локализация `values-fr` (веб и терминал говорят на трёх языках,
Android — на двух). P2P-файлы и wake остаются доступны в дополнительном
прямом режиме.

Проверки текущего этапа:

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew \
  :app:testDebugUnitTest --tests 'net.tailchat.android.cloud.*'
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew :app:assembleDebug
JAVA_HOME=$(/usr/libexec/java_home -v 17) ./gradlew :app:assembleRelease
```

Проект содержит Gradle Wrapper 8.9, поэтому системный `gradle` для сборки не
нужен. Запускайте wrapper под JDK 17: Android lint из AGP 8.7.3 не работает под
JDK 26 и падает при разборе версии `26.0.2.1` внутри IntelliJ `JavaVersion`.

Девять контрактных тестов проверяют register/login/history (включая
`image`/`voice`), Bearer-авторизацию, ошибки сервера, WebSocket auth/ready,
subscribe, обмен текстовыми frames и живой relay file-offer/file-chunk.
Полный набор Android unit-тестов и release-сборка проходят через wrapper.
Подписанный release APK установлен на AVD `tailchat34` и проверен живьём
против продакшен-сервера: регистрация, Saved Messages, отправка текста,
фото (сжатие, инлайн-рендер, полноэкранный просмотр по тапу), файла
(`file-offer`/`file-chunk`/`file-done` через реальный WebSocket, карточка с
прогрессом и размером) и голосового сообщения (запрос `RECORD_AUDIO`,
запись `MediaRecorder`, отправка, воспроизведение через `MediaPlayer`),
а также визуальный терминальный слой: `⧗`/`✓`/`✓✓`-расписки, `●`/`○`
присутствие, `/help`/`/peer` с секционным баром, `:good:`-эмодзи-замена,
и по одному сообщению каждого вида классификации текста (обычное с
кликабельной ссылкой, целиком-цитата, целиком-блок-кода) — без единого
исключения в logcat. Переход в P2P и возврат в cloud тоже проверены на
устройстве.

## Сборка

Нужны JDK 17 и Android SDK с platform 34. Gradle 8.9 уже зафиксирован в
проектном wrapper:

```bash
cd android
export JAVA_HOME=$(/usr/libexec/java_home -v 17) # macOS
./gradlew :app:assembleRelease     # APK, R8 включён
./gradlew :app:assembleDebug       # без минификации
./gradlew :app:testDebugUnitTest   # тесты совместимости с настоящим клиентом
```

`local.properties` указывает на SDK. Версии инструментов зафиксированы:
AGP 8.7.3, Kotlin 2.0.21, Compose BOM 2024.09.00, compileSdk 34, minSdk 29.

## Как устроено

`app/src/main/java/net/tailchat/proto/` — порт протокола из `src/`, один к
одному по поведению:

| Android | оригинал |
|---|---|
| `Frames.kt` | `src/frames.js` |
| `Session.kt` | `src/session.js` |
| `Rendezvous.kt` | `src/rendezvous.js` |
| `Signals.kt` | `src/typing.js`, `src/presence.js`, `src/outbox.js` |
| `FileTransfer.kt` | `src/files.js` |

Всё состояние рандеву живёт на одном потоке (`tailchat-engine`) — так логика из
JS переносится без единого замка. Блокирующее — DNS, `connect`, `accept` —
работает в стороне и возвращает результат туда же. Запись в сокет идёт через
отдельный поток на соединение: Android запрещает блокирующую запись из главного
потока, и правильно — интерфейс не должен замирать из-за пира, который перестал
читать. Файловые чанки едут по тому же пути, но с окном в шесть кадров, и это и
есть backpressure, которое в Node даёт событие `drain`.

Выше протокола: `ChatService` держит канал (foreground service, тип
`specialUse` — ни одна из типовых категорий не описывает «держать P2P-канал», а
брать чужую значило бы получить и её таймаут), `ChatEngine` — всё между проводом
и экраном, `ui/` — Compose.

### Чем отличается авторизация входящих

На компьютере входящее соединение проверяется у локального демона
(`tailscale whois`) — пир не может подделать этот ответ. На телефоне такого
демона нет, поэтому список разрешённых адресов собирается из DNS-имени пира и из
кадра `devices`, который пир присылает по уже установленному каналу. Плюс
сокет слушается на tailnet-адресе, когда он есть, — тогда достучаться из-за
пределов tailnet нельзя вообще.

## Тесты

`app/src/test/java/net/tailchat/proto/InteropTest.kt` поднимает **настоящий**
клиент из `src/` (через `tools/peer.mjs`, который импортирует `startRendezvous`
и `createFileReceiver` напрямую) и гоняет против него код приложения: рукопожатие
с версиями, сообщения в обе стороны, `ack`/`read`, `typing`/`caps`/`focus`,
передача файла на 150 КБ в несколько чанков и приём файла с проверкой контрольной
суммы. Это единственный тест, который может доказать совместимость: чистый
юнит-тест доказал бы только, что порт согласен сам с собой.

```bash
node tools/peer.mjs --peer-host 127.0.0.1 --peer-port 4748 --port 4747 --bind 0.0.0.0
```

Запущенный руками, `peer.mjs` печатает события построчным JSON и принимает
команды тем же форматом на stdin — им удобно проверять приложение живьём.
Стандартный ввод при этом должен быть каналом, а не терминалом: в canonical-режиме
PTY строка длиннее 1024 байт (`MAX_CANON`) обрезается, и кадр с файловым чанком
до программы не доходит.


- `VoiceTalkBackActionsTest` — TalkBack-жест «Forward 10 seconds» на голосовом
  сообщении через настоящий `AccessibilityNodeInfo.performAction`, не через

  свои account/conversation/voice прямо в Room, пишет свою сессию).
- `ChatRepositoryOnDevicePerfTest` — warm-open и local-send commit latency
  (LOCAL_FIRST_EXECUTION_PLAN.md §10) на реальной файловой Room-базе на
  хранилище устройства, диалог из 1000 сообщений; печатает p50/p95/p99/max в
  `Log.i("PerfTest", …)`.

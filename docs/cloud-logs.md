# Шпаргалка: логи Tailchat Cloud

Где смотреть, что читать, что проверять. Все команды — с ноутбука; бокс доступен
как `ssh ovh` (алиас в `~/.ssh/config`, см. AGENTS.md §6 — не по публичному IP).
Служба в PM2 называется `tailchat-cloud` (у него же ещё `tailchat-gateway`; остальные
приложения на боксе к Tailchat отношения не имеют).

## 1. Где лежат логи

| Что нужно | Команда |
|---|---|
| живой поток | `ssh ovh 'pm2 logs tailchat-cloud'` (выход — Ctrl+C) |
| один снимок, без подписки | `ssh ovh 'pm2 logs tailchat-cloud --nostream --lines 200'` |
| stdout (готовность, отчёты деплоя) | `ssh ovh 'tail -n 50 ~/.pm2/logs/tailchat-cloud-out.log'` |
| **stderr — все диагностические строки** | `ssh ovh 'tail -n 50 ~/.pm2/logs/tailchat-cloud-error.log'` |
| пути к файлам, аптайм, перезапуски | `ssh ovh 'pm2 describe tailchat-cloud'` |
| готовность | `ssh ovh 'curl -s -m 5 localhost:7683/health'` → `{"ok":true,"aiBridge":true}` |

При старте служба печатает одну строку: адрес, порт и каталог данных. Все строки,
которые служба пишет сама (`note(...)` в `src/cloud/hub.js`), идут в **stderr**, то
есть в `tailchat-cloud-error.log`. Пароли и токены в лог не попадают ни при какой
ошибке.

## 2. Что вообще пишет служба

| Строка начинается с | Когда появляется |
|---|---|
| `Tailchat cloud ready: http …, data …, ai-bridge: …` | старт службы (одна строка на запуск) |
| `Tailchat cloud: read …` | движение водяного знака прочитанного — кто-то отметил разговор прочитанным |
| `Tailchat cloud: frame budget …` | клиент вышел за бюджет кадров (60/с) — видно логин, собеседника и тип кадра |
| `Tailchat cloud: media …` | одна выдача `GET /api/media` (байты вложения по ссылке) — кто, какая беседа, чем кончилось и сколько байт |

### Строка выдачи вложения

```
Tailchat cloud: media login=roman peer=olga status=200 bytes=262144 ms=3
```

| Поле | Смысл |
|---|---|
| `login` | кто скачивал |
| `peer` | беседа (`-`, если запрос не назвал годного логина) |
| `status` | `200` целиком, `206` часть (`Range`), `304` уже есть у клиента, `404` нет такой записи или скрыта «у себя», `410` удалена для всех **или вытеснена бюджетом** (`media_evicted`), `429` больше 8 одновременных на аккаунт / 32 на процесс, `400`/`403` — плохой запрос / не друг |
| `bytes` | сколько байт тела ушло (0 для отказа и `HEAD`) |
| `ms` | время ответа на сервере |

Ни id сообщения, ни содержимого в строке нет — так задумано
(`docs/specs/2026-11-03-history-media-refs.md` §8.2).

```bash
# сколько вложений люди не успели скачать до вытеснения (ответ на «менять ли бюджет 64 МиБ»)
ssh ovh "grep 'cloud: media' ~/.pm2/logs/tailchat-cloud-error.log | grep -c 'status=410'"
# объём, отданный по ссылкам
ssh ovh "grep 'cloud: media' ~/.pm2/logs/tailchat-cloud-error.log | sed 's/.*bytes=\([0-9]*\).*/\1/' | paste -sd+ - | bc"
```

### Строка прочтения — главная для вопроса «почему уже прочитано»

```
Tailchat cloud: read login=godsheep peer=roman via=web readTs=1759141234567 at=1759141234601
```

| Поле | Смысл |
|---|---|
| `login` | чей аккаунт прочитал |
| `peer` | разговор, который отмечен прочитанным |
| `via` | **какая именно сессия**: `web` — браузер, `android/<build>` — APK (номер сборки), `cli` — терминал или бот |
| `readTs` | водяной знак: ts последнего сообщения, до которого дошло чтение |
| `at` | когда это случилось |

Пишется **только на движение** знака: повторный рецепт уже прочитанного сообщения
молчит, поэтому одна строка = одно настоящее прочтение.

```bash
# последние 20 прочтений
ssh ovh "grep 'cloud: read' ~/.pm2/logs/tailchat-cloud-error.log | tail -20"
# кто читал разговор с roman
ssh ovh "grep 'cloud: read' ~/.pm2/logs/tailchat-cloud-error.log | grep 'peer=roman'"
# что читал конкретный аккаунт
ssh ovh "grep 'cloud: read' ~/.pm2/logs/tailchat-cloud-error.log | grep 'login=godsheep'"
# только по клиенту
ssh ovh "grep 'cloud: read' ~/.pm2/logs/tailchat-cloud-error.log | grep 'via=web'"
# сколько всего
ssh ovh "grep -c 'cloud: read' ~/.pm2/logs/tailchat-cloud-error.log"
```

Зачем это: прочитанность принадлежит **аккаунту и разговору**, а не устройству —
любая своя сессия передаёт подтверждённую ватермарку остальным через `read-sync`.
`via=` называет ту сессию, которой это удалось. Начиная с 1.122 автоматическое
прочтение в web/CLI ограничено показанным входящим сообщением и активным окном
с транскриптом внизу; APK проверяет foreground, открытый разговор и точные
показанные id. Выбор контакта до отрисовки истории сам по себе ничего не читает.
`mark-read` целиком остаётся только явной командой пользователя.
Сервер подтверждает прочтение после записи в журнал, поэтому принятый `read`
восстанавливается даже при падении до следующего снимка `accounts.json`.
Старый путь `onLayoutChange` → `selectPeer` → массовый `mark-read` разобран
в исторической записи worklog «сообщение от roman уже прочитано»; это не
описание нынешнего автоматического поведения.

### Как читать разницу `at − readTs`

| Разница | Что произошло |
|---|---|
| 0–3 с | сообщение прочитано в момент прихода: разговор был открыт, вкладка в фокусе, транскрипт внизу (`messageIsOnScreen`) |
| меньше нуля | сообщение помечено прочтённым *раньше* его собственной метки времени: так бывает, когда часы отправителя ушли вперёд, — сервер правит такое только при разнице больше двух минут |
| минуты и больше | отметку поставили позже: разговор открыли (клик в ростере, «отметить прочитанным», клик по уведомлению) либо в вебе сработал `flushReadReceipts` на возврате фокуса в уже открытый разговор, чьи сообщения пришли, пока окно было не в фокусе или транскрипт стоял прокрученным вверх |

Живой пример (29.09.2026):

```
read login=godsheep peer=hajnowka via=web readTs=…633 → 14:33:52, at=…257 → 14:44:17
```

Разница 625 с: разговор с `hajnowka` отмечен прочитанным через 10.4 минуты после
последнего сообщения в нём, и сделала это **браузерная** сессия (`via=web`).

## 3. Не флапает ли служба

```bash
ssh ovh 'pm2 describe tailchat-cloud | grep -E "status|uptime|restarts|unstable"'
```

* `status online` и `unstable restarts 0` — норма;
* `restarts` — счётчик за всю жизнь записи в PM2, деплой его не сбрасывает, поэтому
  сам по себе он ничего не значит; важна **разница между двумя снимками** без ваших
  деплоев;
* растёт `restarts` без деплоя или `unstable restarts` > 0 → смотреть стектрейс:
  `ssh ovh 'pm2 logs tailchat-cloud --err --lines 40 --nostream'`.

## 4. Проверка релиза (только чтение, ничего не пишет)

```bash
node bin/release-cloud.js --check      # health, ревизия бокса, ?v= в index/sw/app/css, тишина §9 → ждём 7/7
ssh ovh 'cd /opt/tailchat && git log --oneline -1'    # что реально развёрнуто
```

Строка `ok silence: …` снимается с самого стора: проба расшифровывает его тем же
модулем, что и облако, и сравнивает `announcedVersion`, список `release-<версия>` и
число текстов с «release» до и после. Значение `announcedVersion` в норме — `1.68`:
оно не двигается, пока рассылка выключена.

`--check` допускает, что бокс отстаёт на коммиты, которые трогают только доки и
тесты, — это не «не вышел релиз», а «деплоить нечего».

## 5. Логи клиентов (когда виноват клиент, а не сервер)

* **Веб / PWA**: DevTools → Console. Установленное окно «Tailchat Web» — то же
  самое; заголовок окна показывает активный разговор и непрочитанные:
  `(2) 📝 Saved Messages — Tailchat`.
* **Android**: теги у него классовые — `TailchatCloud`, `ChatService`,
  `CloudSessionStore`, `CallController`, `CallEngine`, `CallService`, `CallAudio`,
  `CallRinger`, `CallRingPreview`, `WebRtcEngine`, `SoundEffects` — поэтому фильтр
  по процессу надёжнее, чем по слову:
  `adb logcat --pid=$(adb shell pidof -s net.tailchat.android)`;
  узкий вариант по нужным тегам:
  `adb logcat -s TailchatCloud:V ChatService:V CloudSessionStore:V`.
* **CLI**: транскрипт пишется в `~/.tailchat/peer-cloud-<login>-<hash>.log.enc`, по
  одному файлу на собеседника, и он зашифрован — читать его надо самим клиентом
  (переключившись на разговор), `cat` ничего не покажет. `/logs on|off` показывает
  путь и выключает запись. Свежий `mtime` файла = последний разговор, который этот
  CLI отрисовывал.

## 6. Что делать, когда что-то не так

| Симптом | Первым делом |
|---|---|
| «сообщение уже прочитано, а я его не видел» | `grep 'cloud: read' … \| grep 'peer=<кто>'` — читать `via=` и `at=` |
| «Too many attempts» в клиенте | `grep 'frame budget' …` — там логин, собеседник и тип кадра |
| клиент мигает «connected/offline» | `pm2 describe` (перезапуски) + `tail -n 100` по `-error.log` |
| сайт отдаёт старое | `node bin/release-cloud.js --check` — там же проверка `?v=` |

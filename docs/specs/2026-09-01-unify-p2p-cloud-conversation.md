# Промпт: объединить P2P и Cloud в один разговор в CLI

Скопируй в новую сессию целиком.

---

## Контекст

Веб-клиент Tailchat (`web/cloud/`) показывает разговор с человеком как ОДИН
непрерывный тред независимо от транспорта: direct P2P (⚡-бейдж рядом с
именем в шапке) — это просто более быстрая труба поверх уже установленного
cloud-разговора, история не разделяется.

Терминальный клиент (`src/cli.js`) — нет. `/p2p` и `/cloud` для одного и
того же человека дают ДВЕ РАЗНЫЕ переписки: разный лог (`resolveLogFile`),
разная AI-память (`createPeerMemory`), разный outbox — всё ключуется через

```js
peerKey = isCloudPeer ? `cloud-${cloud.peer}` : (peerLogin ?? args.peer)
```

Переключился с другом с `/p2p` на `/cloud` — история "исчезла" (на самом
деле лежит в другом файле под другим ключом).

Есть уже утверждённый план на эту тему — **прочитай `docs/archive/local+cloud.md`
целиком первым делом**, статус в нём: «Утверждён к реализации» (Tri-Hybrid
Architecture + Offline Identity), от 2026-08-31. Фаза 1 плана (LAN
auto-discovery через `src/lan-discovery.js`, Ed25519-identity через
`src/identity.js`, сертификаты) **уже реализована и подключена** в
`src/cli.js` (импорты на строках ~92-93, использование около ~1462-1567,
релиз `932e836` "v0.60.0 (cloud): Tri-hybrid engine..."). Не реализованы:
**Фаза 2** (единый ростер `/peer`, показывающий lan+tailnet+cloud одним
списком) и **Фаза 3** (автоматический fallback/сквозная маршрутизация:
LAN → Tailscale P2P → Cloud Hub для ОДНОГО и того же разговора) — это и
есть то, что реально «объединяет беседу», и именно этого сейчас нет.

## Почему это сложнее, чем кажется по вебу

Веб построен на ОДНОЙ системе идентичности: cloud-аккаунт (логин/пароль).
"Direct P2P" там — сетевая оптимизация внутри уже известного отношения
(`hub.js`'s `store.areFriends()` уже подтвердил, кто есть кто), никогда не
нужно сверять две разные системы идентификации.

В CLI их ДВЕ параллельных и сегодня НЕ связанных:
- **Tailscale-роутер**: идентификация через `tailscale status`/`whois`,
  peer резолвится по `peerLogin`/hostname/IP роутера, без аккаунта вообще.
- **Cloud-аккаунт**: логин/пароль на сервере, тот же человек может быть
  здесь под СОВЕРШЕННО другим идентификатором (email vs cloud-login vs
  Tailscale display name).

Прежде чем объединять историю, нужно решить: как понять, что «этот
tailnet-пир» и «вот этот cloud-друг» — один и тот же человек? Варианты
(взвесить, не выбирать automatически):
1. Явная ручная привязка пользователем один раз («это тот же человек, что
   и @login в cloud») — просто, но требует лишнего шага от пользователя.
2. Сопоставление по имени/hostname с уверенностью «скорее всего» +
   подтверждение при первом расхождении (fuzzy match) — рискует ложно
   объединить разных людей.
3. Криптографическая связь через уже существующий Ed25519-identity/сертификат
  (Фаза 4 плана в `docs/archive/local+cloud.md`, "Trust On First Use") — самый надёжный,
  но требует, чтобы человек сначала засветил Cloud-identity и P2P-identity
  под одним `pubKey`.

## Что нужно сделать (по мере готовности к реализации, не строго обязательный порядок)

1. **Единый `peerKey`**: заменить `isCloudPeer ? 'cloud-${peer}' : peer`
   идентификатором, который не зависит от текущего транспорта — как
   минимум, когда установлена привязка (см. выше). Затронуты:
   `resolveLogFile`/`defaultLogPath` (`src/log.js`), `createPeerMemory`,
   `outboxFileFor`, все места, где `peerKey` вычисляется в `cli.js`
   (обычный старт сессии — строки ~1652-1654, `switchActiveConversation` —
   ~3109-3111).
2. **Миграция существующих раздельных историй**: у пользователей уже ЕСТЬ
   файлы `<peer>.log` и `cloud-<peer>.log` для одного человека — решить,
   сливать ли их при первом объединении (по времени?) или оставлять как
   раздельный архив и вести новую историю уже объединённо. Нельзя молча
   потерять уже записанные разговоры.
3. **Фаза 2 — единый ростер**: `/peer` и `choosePeer()` должны показывать
   одну строку на человека с всеми доступными транспортами
   (`📡 [lan] / ⚡ [tailnet] / 🌐 [cloud]`), а не по одной на каждый.
4. **Фаза 3 — маршрутизация**: при отправке сообщения в объединённый
   разговор транспорт выбирается автоматически по приоритету
   LAN → Tailscale P2P → Cloud Hub, с fallback на следующий, если текущий
   недоступен — сохранив то, что `/p2p`/`/cloud` уже умеют форсировать
   конкретный транспорт вручную (`args.transport`, `finishSwitch`).
5. **Не сломать существующее**: `test/cli.test.js` (58.6KB) — самый большой
   тестовый файл в репозитории, наверняка много тестов завязано на текущее
   раздельное поведение `isCloudPeer`/`peerKey` — их придётся явно
   пересмотреть, не просто починить до зелёного.

## С чего начать

- Прочитать `docs/archive/local+cloud.md` целиком.
- Перечитать актуальное состояние `src/cli.js` (`isCloudPeer`, `peerKey`,
  `switchActiveConversation`, `resolveCloudPeerSync`) и `src/identity.js`,
  `src/lan-discovery.js` — они могли измениться после 2026-09-01.
- Решить вопрос идентификации (варианты 1-3 выше) — это архитектурное
  решение с реальными компромиссами, обсудить с пользователем явно через
  `ask`, а не выбирать самостоятельно.
- Сначала спроектировать миграцию существующих раздельных историй
  (пункт 2), прежде чем трогать `peerKey` — иначе первый же запуск
  новой версии может выглядеть как потеря переписки.

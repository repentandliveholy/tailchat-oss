# Tailchat: план исправления пароля, галочек и синхронизации

## Задача и границы диагностики

Запрос владельца: исправить неверные галочки; создание дополнительного пароля должно работать начиная с одного символа; Web, CLI и APK должны синхронизироваться; APK не должен опаздывать или терять сообщения.

Это передача работы другому агенту, **не отчёт об исправлении**. Исходники приложения не менялись, production и пользовательские аккаунты не затрагивались. Исследован локальный код: package.json 1.96; Android versionName 0.76.41/versionCode 146. Соответствие установленному APK и production не проверялось.

Доказательства: чтение исходников; исполнение настоящих функций Web в Node VM с изолированным окружением; настоящий createAccountStore во временных каталогах; настоящий createCloudHub с четырьмя подключениями через его транспортный интерфейс. Сетевой браузерный UI, Android runtime, FCM, Doze и физический телефон не проверялись. Полный test suite не запускался: это диагностика, не изменение поведения.

## 1. Найденные причины

### P0 — Web запрещает изменение только дополнительного пароля

**Воспроизведено исполнением onProfileSubmit.**

`web/cloud/app.js:9952–10037`, особенно 9970–9975:

```js
const changingMainPassword = Boolean(currentPassword || newPassword || confirmPassword);
```

Текущий основной пароль нужен для подтверждения изменения дополнительного, но уже одно его наличие включает смену основного. Если поля нового основного пароля пустые, форма возвращает invalid_password до обращения к серверу.

Воспроизведение: currentPassword = `1234567890`, extraPassword = extraPasswordConfirm = `abcdefghij`, checkbox включён, оба поля нового основного пустые. Результат: `profileStatus=invalid_password`, `httpCalls=0`.

Серверный `updateProfile` и последующий `login` проверены отдельно: дополнительный пароль `x` и `abcdefghij` успешно устанавливаются и принимаются. Менять минимум на сервере ради этой ошибки не требуется. См. `src/cloud/accounts.js:1043–1125`.

Дополнительный дефект метаданных: `hub.js:625–629` отправляет self только с login/name, а `app.js:8858–8862` целиком заменяет self. Признак extraPasswordEnabled из HTTP-авторизации теряется после ready. Форма использует его для решения «включить/оставить/выключить». Это вывод из кода, отдельно в UI не воспроизводился.

### P0 — после включения дополнительного пароля APK не умеет войти

**Подтверждено интерфейсами исходников.**

`android/.../cloud/CloudApi.kt:37–42`: login отправляет только login/password/pubKey. `CloudController.kt:106,730–731` не принимает extraPassword. `ui/CloudScreen.kt:3651` вызывает именно этот интерфейс. У Web есть двухшаговый вход; у APK необходимого поля протокола нет.

Поэтому нельзя выпускать только исправление Web-формы: существующая APK-сессия может продолжать работать, но повторный вход в защищённый аккаунт останется заблокированным.

### P0 — Android путает собственное прочтение с прочтением собеседника

**Серверная форма события воспроизведена; Android-ошибка установлена по коду.**

`accounts.js:1657–1672,2223–2248` создаёт read для обеих сторон: `self:true` у читателя, отсутствующий/false self у автора сообщения.

Локальная проба: Anna отправила сообщение Boris, Boris прочитал. В логе Anna получено `{kind:'read', peer:'boris', id, readTs, readAt}`; в логе Boris — соответствующее событие с `peer:'anna', self:true`.

Но `SyncEngine.kt:1491–1495` в обоих случаях вызывает readWatermark и suppressReadNotifications. `ChatRepository.kt:553–554` обновляет собственный readWatermarkTs (`data/Daos.kt:108–118`), а не peerReadTs и не галочки исходящих.

Следствие по коду: пропущенная live-квитанция не восстанавливает Read через sync; чужое прочтение может ошибочно подавлять уведомления о собственных непрочитанных входящих.

Дополнительно live-путь `SyncEngine.kt:732–737` продвигает только receipt.id. Web трактует read как watermark и обновляет предыдущие сообщения (`app.js:9250–9277`); Android делает это лишь при загрузке истории (`ChatRepository.kt:464–487`). Отсюда разные галочки при пропущенных ранних read и полученном позднем read.

### P0 — активное соединение APK вне диалога не получает полную account-sync информацию

**Воспроизведено настоящим hub без pushSender.**

Четыре подключения: Anna Web подписана на Boris; Anna APK без подписки; Boris Web подписан на Anna; Boris APK без подписки. После ready и subscribe Anna отправляет сообщение:

- Anna Web: message-accepted;
- Boris Web: frame/msg;
- Anna APK: нет событий;
- Boris APK: нет событий.

Причины:

- `hub.js:814–818`: собственные сообщения отправляются только сессиям, подписанным на этот диалог;
- `hub.js:941–966`: входящие live-frame тоже зависят от подписки;
- `hub.js:1019–1027`: conversation-update получают только webFeatures;
- `hub.js:1043–1064`: native unread идёт только если вообще не было доставившей сессии; открытая Web-сессия блокирует этот путь для APK;
- `SyncEngine.kt:605,1369–1381,1437–1438`: sync запускается на ready и продолжается страницами; непрерывного account-feed или запроса sync по каждой новой серверной мутации нет.

Push в production может разбудить APK-получателя, но не является гарантией; push направляется получателю, не второму устройству отправителя (`hub.js:1065–1072`). Открытие диалога/reconnect могут позднее закрыть разрыв — это механизм задержки, а не доказательство удаления сообщения сервером.

### P0 — Android подтверждает курсор раньше восстановления содержимого; одной страницы истории недостаточно

**Граница страницы воспроизведена; порядок Android установлен по коду.**

`SyncEngine.kt:1400–1415` коммитит cursor вместе с применением метаданных событий, затем отдельно вызывает HTTP loadHistory для отсутствующих сообщений. Результат loadHistory игнорируется. `1549` превращает HTTP-ошибку в false.

Событие message не содержит текст/медиа (`accounts.js:1676–1677`). Следовательно, запись cursor ещё не доказывает, что содержание сохранено. Существующий historySeeded=false частично помогает при следующем reseed, но не фиксирует перечень конкретных недостающих ID; в пределах соединения prefetched препятствует повторному prefetch (`SyncEngine.kt:1641–1667`).

`CloudApi.kt:46–101` запрашивает единственную `/history?peer=...&deleted=1`, без limit/before/beforeId и без продолжения. Сервер по умолчанию отдаёт 200 (`server.js:34,973–993,1151–1154`). Проба с 205 новыми записями: история = 200, page-1 отсутствует, событие page-1 всё ещё есть в eventsSince. Повторная загрузка той же последней страницы дыру не закроет; увеличение лимита только отодвинет проблему.

Отдельно проверить reset: `SyncEngine.kt:1387–1391` помечает все диалоги unseeded, но явно обновляет только открытый. Старый набор prefetched и порядок prefetch/resync могут оставить остальные незасеянными.

### P0 — Web теряет отправку при гонке подписки

**Воспроизведено настоящими onComposerSubmit/sendFrame в VM.**

`app.js:5086–5128`: сначала создаётся локальная строка, затем вызывается sendFrame без проверки результата, затем очищается composer.

`app.js:9651–9664`: при subscribedPeer !== to возвращается false. Проба: authed=true, activePeer=boris, subscribedPeer=anna. Итог: одна локальная строка, пустой draft, ноль отправок. Такое сообщение не могло появиться на APK, поскольку не попало на сервер.

`handleEnvelope` Web не обрабатывает message-accepted/sync-page; auth `app.js:8733` не объявляет durable-ack/sync-v1. `src/cloud/link.js` также не обрабатывает эти envelopes; caps на 585 — marked-unread-v1/reply-reminder-v1. Это отдельный разрыв контрактов, не повод считать любой socket.send доказательством сохранения.

### P1 — Android отправляет ack/read до успешного сохранения входящего

**Риск гонки по исходникам; требуется fault-injection тест.**

`SyncEngine.kt:675–719` запускает repository.applyIncoming в coroutine; `720–723` вне неё сразу ставит ack/read в очередь. При отказе Room/медиакеша сообщение может быть уже подтверждено. Более раннее read-accepted может также прийти до появления строки. Перенести принятие ответственности за receipt за границу успешного commit.

Другой риск порядка: `SyncEngine.kt:676–690` заменяет серверный ts входящего на previewTs+1. Задержанное/повторное сообщение может получить иной порядок и перестать совпадать с readTs. Сохранить серверный порядок; не чинить расстановку сообщений подменой timestamp. Проверить также применение accepted.ts: callback на 727–729 передаёт дальше seq, но не ts.

### P1 — режим Direct несовместим с полной cloud-синхронизацией в текущем виде

**Воспроизведён выбор транспорта; это проектный конфликт, не случайная ошибка.**

`app.js:9646–9664`: при открытом data channel содержимое идёт только P2P, сервер его не видит. Проба sendFrame(msg): вызван только direct, server не вызван. Получатель обрабатывает его локально (`9748–9751`). Поэтому серверная история, третье устройство и APK не имеют источника для восстановления такого сообщения.

Не добавлять скрытую отправку содержимого на сервер: комментарий явно обещает обратное. Для синхронизируемых cloud-диалогов рекомендован серверный durable commit как источник истины. Перед изменением обещания приватности Direct нужен явный выбор владельца: cloud-синхронизация с серверным хранением либо отдельный честно обозначенный несинхронизируемый Direct-режим. Локальный/tailnet P2P вне cloud не переделывать.

## 2. Единый контракт до начала правок

1. Идентичность сообщения — аккаунт/диалог/автор/id; retry сохраняет исходный id. Ни дедупликация, ни квитанция не должны затронуть чужой диалог с совпавшим id.
2. Для cloud-сообщений состояния: Queued/Sending → Accepted (сервер durably committed) → Delivered (устройство получателя durably stored) → Read (согласованный read-watermark). Нет доказательства — нет повышения состояния. Поздний Accepted/ack не понижает Read.
3. Сохранить нынешнюю общую легенду: часы до Accepted, одна галочка Accepted/Delivered, две Read. Не вводить новые значения цветов/иконок отдельно на одном клиенте. Failed — отдельное состояние ошибки, не арифметически «выше Read»; Android ordinal уже хранится в БД, не переставлять enum.
4. ownRead и peerRead — разные монотонные поля. read.self=true обновляет чтение этого аккаунта; false — чтение собеседника/исходящие галочки. Передавать явный watermark, не требовать наличия одного конкретного bubble для применения read.
5. Подписка/view interest управляет отображением и эфемерными событиями, но не полнотой durable account-sync. FCM — ускоритель, не источник истины.
6. Cursor означает «содержимое применено либо обязательство его загрузить надёжно сохранено». Ошибка сети/процесса не может забыть эту обязанность.
7. Один порядок сообщений для всех устройств. Использовать существующие seq и серверные ts; при расширении протокола сначала зафиксировать порядок/tie-break. Не сравнивать watermark с искусственно увеличенным локальным ts.
8. Для пароля: 1–200 символов, без trim/pad на уровне UI; existing серверное хеширование не менять в рамках этой задачи. extraPassword: отсутствует — оставить; строка — установить; существующий empty/null-контракт — удалить только с проверкой основного пароля. Единицу длины Unicode согласовать с текущим API, не менять скрыто.
9. Контрольные hello/read/ack не включать в SELF_SYNC и не эхо-отправлять на полученные account-local события. Сохранить запрет ping-pong из AGENTS.md.

## 3. Последовательность реализации

### A. Исправить пароль сквозным изменением Web + Android

- В onProfileSubmit вычислять смену основного только по полям нового основного/подтверждения. currentPassword — доказательство полномочий для обеих независимых операций.
- Сохранить проверку подтверждения и 1–200; не требовать новый основной для set/change/clear дополнительного.
- Передавать extraPasswordEnabled в canonical public self на ready и profile либо безопасно объединять профиль без потери полей; не создавать два расходящихся publicUser-контракта.
- Добавить extraPassword в Android CloudApi → CloudController → экран входа/состояние. На extra_password_required показать поле и продолжить тот же вход; неверный пароль должен сохранять корректную серверную семантику ошибок и limiter. Не логировать и не сохранять plaintext секреты.
- Если управление дополнительным паролем требуется прямо в APK, использовать тот же PATCH /profile и три состояния поля, а не отдельный endpoint. Минимально обязательный cutover — вход APK после включения защиты через Web.
- Перед изменением экспортируемых JS-символов проверить LSP references; Kotlin callers перечислить и обновить полностью. CLI уже передаёт дополнительный пароль (`src/cloud/api.js`, `prompt.js`), проверить совместимость, не переписывать готовый путь.

### B. Исправить receipt reducer и сохранить серверные факты

- Разделить обработку read.sync по self в Android; добавить атомарный repository-путь peerRead, продвигающий все подходящие own messages и peerReadTs. Не использовать markSeeded для простой квитанции: чтение не доказывает полноту истории.
- Для live-read доставлять readTs вместе с id/readAt; одинаково применять live, sync и HTTP-history. Older receipt никогда не откатывает watermark.
- Передавать/применять accepted.ts и seq; не перетаскивать входящие в конец посредством previewTs+1. Повторный msg не меняет исходный timestamp/порядок.
- Ставить ack/read только после успешного сохранения входящего; провал БД не должен сообщать Delivered/Read. Read additionally требует реальной видимости/явного mark-read, а не просто загрузки истории.
- Для Delivered определить восстановление после переустановки/нового устройства: сейчас серверный history гарантирует Accepted и peerRead, но не хранит ack как долговечное delivery-событие. Либо хранить device-ack как факт в журнале/проекции, либо не обещать межклиентную точность Delivered. Read и Accepted синхронизировать обязательно.

### C. Устранить дырки account-sync и истории

- Предпочесть существующий sync-v1, а не второй протокол сообщений. После durable mutation адресно уведомлять все сессии затронутых аккаунтов о доступном sync; capability-gated wake-up с coalescing, без отражения control frames. Альтернатива — поток страниц того же feed; зафиксировать один контракт.
- В клиентах один последовательный sync pump на аккаунт/generation; следующий запрос учитывает сохранённый cursor и события, появившиеся во время текущего прохода. Возврат foreground/reconnect закрывает разрыв независимо от push.
- Для неизвестного message.id транзакционно сохранять обязанность backfill вместе с cursor (допустимо существующее состояние, только если оно действительно гарантирует повтор и нужные ID). Не держать Room-транзакцию во время HTTP. Crash после cursor и до HTTP обязан восстанавливаться после запуска.
- CloudApi.history должен поддержать реальную пагинацию. Использовать уже имеющиеся before+beforeId для одинаковых timestamps (`server.js:980–990`); не заменять это limit=5000. Загружать до закрытия требуемого диапазона/всех недостающих ID либо до достоверного конца серверной истории.
- Не помечать диалог полностью seeded по одной последней странице. Не терять tombstone/hidden semantics, не воскрешать удалённое, не трогать pending outbox при reseed.
- Неудавшаяся загрузка должна оставаться retryable; prefetched не должен навечно блокировать её в текущем соединении. reset переинициализирует обязанность reseed всех нужных диалогов, не только активного.
- Проверить account/generation на применении async-ответов и не допустить старой страницы откатить cursor после нового соединения.

### D. Привести Web и cloud-CLI к тому же durable send/sync контракту

- Web: до очистки composer сохранить pending intent. Отправка ждёт корректной маршрутизации/subscription либо использует addressed-send capability. Положительный socket.send не снимает pending; message-accepted снимает, потерянный ack ведёт к retry того же id. Переходы UI соответствуют контракту B.
- Сохранность pending после reload обязательна, иначе часики лишь маскируют потерю. Переиспользовать текущие storage/retry механизмы где они есть; не добавлять параллельный outbox рядом с существующим.
- Cloud-CLI: провести accepted/sync через src/cloud/link.js к владельцу очереди/истории, найденному через references; не менять локальный P2P transport-контракт вслепую. Проверить чтение на третьем устройстве и восстановления после offline.
- Web должен применять account-sync к уже закешированным неактивным диалогам, не полагаться исключительно на повторное открытие/страницу reload.
- Решение по Direct из раздела 1 принять до заявления «все клиенты синхронизированы»; ни тайно загружать P2P-содержимое, ни молча исключать этот режим из обещания нельзя.

Работы A и Android receipt reducer можно вести независимо после фиксации контракта. Hub/feed/API-изменения назначить одному владельцу. SyncEngine.kt одновременно затрагивают B и C: один интегратор/последовательные правки, не конкурентная перезапись. Никаких общих build/test во время параллельных изменений; итоговая проверка после интеграции.

## 4. Приёмка и доказательства

### Регрессионные сценарии, заслуживающие постоянного теста

1. Web: включить extraPassword длиной 1 и 10, сменить/отключить без нового основного; primary login после операции не изменён. Неверный currentPassword, mismatch, >200 отклоняются; отсутствие поля не сбрасывает защиту. ready/reconnect не теряет enabled. Android и CLI входят в тот же защищённый аккаунт.
2. Anna отправляет m1/m2, Boris читает m2; ранний read для m1 намеренно потерян. Все устройства Anna показывают оба Read, включая после reconnect и history merge. Поздние Accepted/ack не понижают состояние.
3. Read от Boris не сбрасывает собственные непрочитанные Anna/уведомления; read на втором устройстве Anna сбрасывает именно её unread. Проверить оба self направления одного реального серверного события.
4. Четыре устройства, как в локальной пробе: оба APK вне диалога, Web-получатель внутри; FCM отключён в изолированном окружении. Собственное/входящее сообщение появляются на APK без принудительного reconnect, открытия диалога или перезапуска. Поставить измеримый локальный timeout с запасом на sync debounce; push не участвует в доказательстве.
5. Offline gap >200 сообщений и совпадающие ts на границе страницы. После sync все доступные серверу IDs/контент присутствуют ровно один раз; более старый пропуск не теряется за новыми 200.
6. Разорвать HTTP-backfill, завершить процесс после записи cursor, перезапустить, дать reset. Обязанность восстановления переживает каждый шаг; outbox остаётся целым.
7. Отказ записи Room/медиа: ни ack, ни read до успешного commit; поздний повтор доставляет сообщение без дубликата и с правильными галочками.
8. Web: submit до subscribed; закрыть сокет после send и до accepted; потерять accepted; reload с pending. Текст не пропадает, server хранит ровно один id, APK получает тот же id. Аналогично cloud-CLI.
9. Поздний старый msg, duplicate msg, скорректированный сервером timestamp, history после live/read: одинаковый порядок и монотонные receipt на всех клиентах.
10. Direct: отдельный тест выбранного владельцем контракта. Не выдавать успех cloud-sync для сообщения, о котором сервер ничего не знает.

Расширять существующие behavioral suites: `test/cloud-accounts.test.js`, `test/cloud-server.test.js`, `test/cloud-hub.test.js`, `test/web-preload-receipts.test.js`; Android `CloudApiTest`, `CloudSocketTest`, `SyncEngineReadAckTest`, `SyncEngineReadReceiptTest`, `SyncEngineReconnectNotificationGapTest`, `SyncEngineHistoryAcceptanceTest`, `SyncEnginePrefetchTest`, `SyncEngineQueuedSendTest` и repository tests. Существующие reconnect-тесты проверяют небольшие успешные backfill; не считать их доказательством >200/failure/crash/live-other-session сценариев.

## 5. Завершение реализации и выпуск

Только после успешного smoke убрать временные скрипты, актуализировать затронутые существующие контракты/документацию. Записать русский итог в начало docs/worklog.md и Android-часть в android/HANDOFF.md; не публиковать пользователям объявления.

Текущий запрос разрешает диагностику и план, **не выпуск или изменение пользовательских аккаунтов**. Реализующий агент должен получить точное разрешение на публикацию/перезапуски в точке риска. После разрешения пользовательские исправления Web/cloud и APK выпускаются вместе по правилам репозитория:

- сверить текущие версии, увеличить package version и синхронно index.html/sw.js ?v, CACHE_NAME и ожидаемый marker test/cloud-sw.test.js;
- увеличить Android versionCode; сохранить WebRTC R8 keep org.jni_zero;
- согласованный commit/push, затем с ноутбука `node bin/release-cloud.js` и `node bin/release-android.js`; не запускать server-only production-deploy локально;
- SSH только через ovh; не restart all и не затрагивать посторонние PM2-сервисы;
- проверить health, deployed revision/cache-busted app.js, APK SHA-256/versionCode и реально обновлённый клиент;
- RELEASE_ANNOUNCEMENTS оставить false; сообщений release-<version> и push-объявлений нет, announcedVersion не продвигается. Контакты tailchat/tailik остаются.

План отката подготовить до публикации: предыдущий серверный релиз без потери нового журнала/данных; Android откат кода только с новым большим versionCode и совместимой Room-схемой. Если добавлено поле/таблица backfill или receipt, миграция обязана сохранить pending messages и курсоры; destructive migration недопустима.

Критерий завершения: каждый принятый сервером cloud-message сходится по id, содержимому и read-состоянию на всех поддержанных клиентах; каждый ещё не принятый виден как pending/ошибка и не теряется; дополнительный пароль работает от одного символа и не лишает APK возможности входа. Ни один из этих критериев не подтверждён одним только compile/test-pass.

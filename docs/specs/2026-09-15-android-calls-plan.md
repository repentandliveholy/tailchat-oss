## 0. Границы работы

**В объёме:**

* 1:1 **аудиозвонок** между двумя аккаунтами Tailchat Cloud, только в
  Android-приложении (`android/`): исходящий, входящий, отклонение,
  сброс, пропущенный, звонок при закрытом приложении.
* Минимально необходимые изменения на сервере (`src/cloud/hub.js`,
  `src/cloud/fcm.js`, `src/cloud/server.js`) и новая служба TURN на `ovh`.

**Вне объёма (сознательно):**

* Видео — **не в этой очереди** (§9.3), возможно позже отдельной задачей.
  В этой очереди не проектируются ни UI, ни битрейт-политики, ни ориентация
  экрана; но и решений, закрывающих дорогу видео, не принимается — см.
  §9.3 о том, что это значит на практике.
* Групповые звонки (нужен SFU — отдельный проект).
* UI звонков в web-клиенте (`web/cloud/app.js`) и в CLI — **не в этой
  очереди** (§9.4), web возможен позже. Проверено: `handleFrame`
  (`web/cloud/app.js:7936` и далее) — плоская цепочка `if (frame.t === …)`
  без завершающего `else`, так что кадры `call-*` там просто игнорируются,
  без ошибок и без разрыва сокета. Сценарий §7.8 это подтверждает на живом
  клиенте.
* Запись звонков, шифрование поверх DTLS-SRTP (DTLS-SRTP уже есть в
  WebRTC), история звонков на сервере.

**Почему «только APK» всё равно требует сервера.** Сигналинг в исходном коде
доставлялся только тому соединению, которое *уже открыло именно этот
разговор*: `deliverFrame` пропускал цель, если `target.peer !== fromLogin`.
Звонок по определению приходит тогда, когда у собеседника открыт другой
разговор, ростер или вообще ничего. Обойти это на клиенте нельзя. Отправка,
наоборот, была возможна без подписки: Android объявляет `addressed-send`
(`CloudSocket.kt`, `CLIENT_CAPS`), а `relay` разрешает адресную отправку
любому другу.

## 1. Решение по транспорту

**Берём libwebrtc** (`io.github.webrtc-sdk:android`), сигналинг — существующий
облачный WebSocket.

Проверено: `150.7871.01` — последняя версия в Maven Central (метаданные
обновлены 2026-09-05), AAR 46 MiB на четыре ABI; `137.7151.05` — 45 MiB,
`125.6422.07` — 41 MiB. Пин: **`150.7871.01`**, откат на `137.7151.05` если
всплывут проблемы сборки с AGP/NDK.

Отклонённые варианты и почему:

| Вариант | Почему нет |
| --- | --- |
| Свой Opus (`MediaCodec`) поверх облачного релея | Пришлось бы писать джиттер-буфер, AEC, AGC, NS, контроль перегрузки и NACK. Без эхоподавления разговор по громкой связи невозможен физически, а аппаратный AEC доступен только через `AudioRecord` в режиме `VOICE_COMMUNICATION` + собственную подстройку — это месяцы работы и худший результат. |
| P2P-путь `net.tailchat.proto.*` (`Rendezvous.kt`) | Работает только внутри tailnet: обе стороны должны быть в Tailscale. Телефоны в LTE вне tailnet — основной сценарий звонка. |
| `android.telecom` self-managed `ConnectionService` | Даёт корректную интеграцию с системной звонилкой и `phoneCall` FGS-тип, но требует `MANAGE_OWN_CALLS`, отдельного жизненного цикла и тонкостей на каждом OEM. Отложено: возможная фаза 9, не блокирует ничего в фазах 1–8. |
| Готовый SDK (LiveKit/Jitsi) | Тянет сервер-компонент и свою модель комнат; для 1:1 это лишний слой и +20 МБ. |

## 2. Протокол сигналинга

Все кадры идут существующим конвертом `{"k":"frame","to":<login>,"d":{…}}`,
то есть через `relay()` → `deliverFrame()`. Namespace `call-*`, **не** `rtc-*`:
`rtc-offer/rtc-answer/rtc-ice` уже заняты апгрейдом web-разговора до
data-channel (`web/cloud/app.js`), и путать SDP голосового звонка с SDP
data-канала нельзя.

```
call-offer  { t, callId, sdp, media:"audio", ts }
call-ring   { t, callId }                      // «устройство проснулось, звоню»
call-answer { t, callId, sdp }
call-ice    { t, callId, candidates:[{candidate,sdpMid,sdpMLineIndex}] }
call-end    { t, callId, reason }               // hangup|declined|busy|timeout|failed|unsupported
call-taken  { t, callId }                       // адресуется СВОЕМУ логину
```

* `callId` — UUID, генерирует инициатор; кадр с чужим `callId` игнорируется
  без ответа (защита от рассинхрона после сброса).
* `call-ice` — **массив**, а не кадр на кандидата: бюджет кадров 60/с на
  соединение (`frameRateLimit`, `src/cloud/hub.js`), и три окна перебора
  подряд закрывают сокет (`RATE_STRIKE_LIMIT`). Клиент копит кандидатов
  150 мс и максимум 20 в кадре.
* SDP аудио-оффера ≈ 2–4 КБ, лимит кадра — 10 МиБ + 1 КБ
  (`CLOUD_FRAME_MAX_CHARS`, `src/cloud/limits.js`), запас огромный.
* `call-taken` — для мультидевайса: устройство, принявшее звонок, шлёт его
  **на свой же логин**; `relay` это разрешает (`to === conn.login`), правило
  маршрутизации §3.1 раздаёт его остальным своим сессиям, а `excludeConn`
  не даёт вернуться отправителю.
* Столкновение (оба звонят одновременно): выживает оффер того, чей логин
  лексикографически меньше — ровно тот же детерминированный tiebreak, что
  уже применён в web (`isDirectInitiator`, `web/cloud/app.js`).
  Проигравшая сторона рвёт свой исходящий и принимает входящий как
  единственный звонок.
* Таймауты: инициатор ждёт `call-ring` 10 с (нет — «абонент недоступен»,
  но звонок продолжает звонить до 45 с ради разбуженного пушем клиента),
  общий звон — 45 с, затем `call-end{reason:"timeout"}` с обеих сторон.

## 3. Изменения на сервере (минимум, 3 файла + coturn)

### 3.1 `src/cloud/hub.js`

1. Новый набор рядом с `QUEUEABLE`/`SELF_SYNC`:

   ```js
   const CALL_SIGNAL = new Set(['call-offer','call-ring','call-answer','call-ice','call-end','call-taken']);
   ```

2. В `deliverFrame` — единственное правило маршрутизации, которое
   добавляется: для `CALL_SIGNAL.has(d.t)` кадр уходит **всем**
   авторизованным соединениям получателя, независимо от `target.peer`.
   Ни истории, ни `store.enqueue` (в `QUEUEABLE` не добавляем: оффер
   пятиминутной давности — это не звонок), ни `conversation-update`,
   ни `selfSync`.

3. Пуш — только для `call-offer` и только если ни одно соединение
   получателя кадр не приняло (`delivered === 0`): вызов
   `pushSender.notify(toLogin, { kind: 'call', callId, peer: fromLogin,
   title: store.nameOf(fromLogin) })`. Именно `delivered === 0`, в отличие от
   безусловного пуша для сообщений: живой сокет уже показал звонок, второй
   канал даст второй звон.

4. `SERVER_CAPS` += `'call-v1'`. Клиент без этой капы в `ready` прячет
   кнопку звонка и на входящий `call-offer` отвечает
   `call-end{reason:"unsupported"}` — «старый сервер» должен выглядеть как
   отсутствие функции, а не как молчащий звонок.

5. Анти-абьюз: не более 5 `call-offer` в минуту на пару (логин→логин),
   лишние — `fail(conn,'too_many_calls',…)` c русским текстом в `MESSAGES`.
   Блок и не-дружба уже отсекаются в `relay` — новых проверок не нужно,
   но тесты на это обязательны.

6. Признак «этому логину можно звонить» (следствие §9.4). У хаба уже есть
   `aiCapable`-карта, заполняемая из кадра `caps` — по тому же образцу
   вводится учёт «есть живое соединение, объявившее `call-v1`», и поле
   `callable: boolean` добавляется в запись ростера `usersFor` и в
   `subscribed`. Живых соединений с `call-v1` нет — `callable: false`, и
   Android прячет кнопку звонка вместо звонка в пустоту. Учёт снимается при
   закрытии последнего соединения логина, там же, где снимается `presence`.

### 3.2 `src/cloud/fcm.js`

`notify` кладёт `{peer,messageId,login,scope,tag}`. Добавить `kind`
(по умолчанию `'msg'`, для звонка `'call'`) и `callId`, а для звонка —
`android: { priority: 'high', ttl: 0 }`: просроченный звонок доставлять
бессмысленно и вредно. Блок `notification` по-прежнему НЕ добавляем
(иначе второе уведомление на то же событие). Web Push (`src/cloud/push.js`)
для звонков не задействуется вообще.

### 3.3 `src/cloud/server.js` — `GET /tailchat/api/turn`

Bearer-токен сессии, ответ:

```json
{ "ttl": 600,
  "iceServers": [
    { "urls": ["stun:203.0.113.10:3478"] },
    { "urls": ["turn:203.0.113.10:3478?transport=udp",
               "turn:203.0.113.10:3478?transport=tcp"],
      "username": "1757900000:roman",
      "credential": "<base64(HMAC-SHA1(secret, username))>" } ] }
```

* Маршрут обязателен добавить в allowlist маршрутов — иначе он не будет
  отвечать.
* Секрета нет → отдаём только STUN-часть. Принцип «облако опционально»
  распространяется и на TURN: без него звонок работает там, где NAT
  позволяет, и честно падает в «не удалось соединиться» там, где нет.
* TTL 600 с; клиент перезапрашивает перед каждым звонком, ничего не кэширует
  дольше.

### 3.4 coturn на `ovh`

Проверено по факту (до установки): `turnserver`/`coturn` не установлены,
порты 3478/5349 свободны (`ss -lun`/`ss -ltn`), 6 CPU, 11 ГБ RAM,
Ubuntu 25.04, **ufw активен**.

```
listening-port=3478
fingerprint
use-auth-secret
static-auth-secret=<из /var/lib/tailchat-cloud/turn_secret, chmod 600>
realm=repentandliveholy.org
min-port=49160
max-port=49200
no-multicast-peers
no-loopback-peers
no-cli
listening-ip=203.0.113.10
relay-ip=203.0.113.10
external-ip=203.0.113.10
denied-peer-ip=10.0.0.0-10.255.255.255
denied-peer-ip=172.16.0.0-172.31.255.255
denied-peer-ip=192.168.0.0-192.168.255.255
denied-peer-ip=127.0.0.0-127.255.255.255
denied-peer-ip=100.64.0.0-100.127.255.255
```

**Критично:** на этой машине живут Tailscale (`41641/udp`, `100.64.0.10`) и
WireGuard (`10.66.66.0/24`, `10.88.31.0/24`). TURN без `denied-peer-ip`
превращается в прокси во внутренние сети — это не «желательная
настройка», а обязательная часть задачи.

`listening-ip`/`relay-ip`/`external-ip` в первой редакции плана
отсутствовали и были добавлены по факту установки (worklog, седьмая часть):
без них coturn слушает и релеит **на всех локальных интерфейсах**, включая
Tailscale и WireGuard, а `denied-peer-ip` фильтрует адрес *назначения*, а не
то, с какого локального адреса coturn готов релеить. Без явной привязки
`denied-peer-ip` сам по себе не был бы полной защитой.

ufw: `allow 3478/udp`, `allow 3478/tcp`, `allow 49160:49200/udp`
(обе цепочки, IPv4 и IPv6).

TLS-порт 5349 — **не** в этой фазе: coturn нужен доступ к сертификатам
Caddy (`/var/lib/caddy/...`), это отдельный хук обновления сертификата.
Ставится, если ручной тест §7 покажет сети, где UDP/TCP 3478 заблокирован.

Приёмка: `turnutils_uclient` на публичный адрес работает; попытка relay на
`100.64.0.10` отклоняется (`403 Forbidden IP`).

## 4. Изменения в Android-приложении

### 4.1 Сборка (`android/app/build.gradle.kts`)

```kotlin
implementation("io.github.webrtc-sdk:android:150.7871.01")
```

* `ndk { abiFilters += listOf("arm64-v8a", "armeabi-v7a") }` — решение
  владельца (§9.1): 32-битные телефоны поддерживаются. Из 4 ABI в AAR
  x86/x86_64 выброшены; для отладки на x86-эмуляторе `x86_64` добавляется
  только в debug-вариант, в release его нет.
  Self-update раздаёт **один универсальный APK**
  (`web/cloud/tailchat.apk`, `AppUpdateApi`), сплиты сломали бы обновление,
  поэтому размер — общий для всех: текущие 4.97 МБ → ожидаемо 13–16 МБ.
  **Фаза 0 обязана измерить и записать факт.** Обязательный парный шаг:
  ленивая инициализация движка в `runCatching` и скрытая кнопка звонка
  там, где движок не поднялся — см. §9.1.
* `proguard-rules.pro`: `-keep class org.webrtc.** { *; }` и
  `-keepclasseswithmembernames class * { native <methods>; }` — libwebrtc
  зовёт Java из JNI по именам, R8 (`isMinifyEnabled = true`) иначе
  вырежет колбэки и звонок упадёт только в release-сборке.

### 4.2 Манифест

Добавить: `MODIFY_AUDIO_SETTINGS`, `USE_FULL_SCREEN_INTENT`,
`BLUETOOTH_CONNECT` (фаза 5). `RECORD_AUDIO`, `FOREGROUND_SERVICE_MICROPHONE`,
`WAKE_LOCK`, `POST_NOTIFICATIONS` уже есть.

Новые компоненты:

```xml
<service android:name=".call.CallService" android:exported="false"
         android:foregroundServiceType="microphone" />
<activity android:name=".call.CallActivity" android:exported="false"
          android:launchMode="singleInstance"
          android:showWhenLocked="true" android:turnScreenOn="true"
          android:excludeFromRecents="true" />
```

Почему отдельная служба, а не `ChatService`: у `ChatService` один
`startForeground(ID_STATUS, …, FOREGROUND_SERVICE_TYPE_SPECIAL_USE)`
и своя логика promote/demote с 10-секундной отсрочкой (`ACTION_GRACE_MS`).
Подмешивать туда тип `microphone` и второй жизненный цикл — прямой путь
сломать уже отлаженную доставку сообщений.
Почему отдельная Activity, а не маршрут в `MainActivity`: нужны
`showWhenLocked`/`turnScreenOn`, а `MainActivity` — `singleTop` с
осознанно выбранным режимом.

> **Фактическое отступление (реализация, коммит `0045fa7`).** Отдельный
> `CallService` не создан: действия уведомления
> (`ACTION_CALL_ANSWER/DECLINE/HANGUP`) обрабатываются в
> `ChatService.onStartCommand`, который уже объявляет
> `specialUse|microphone` и уже владеет единственным `CallController`.
> Логика `ACTION_GRACE_MS` не тронута, только читается уже объявленный тип.
> Решение помечено к перепроверке на реальных устройствах (§7): если второй
> тип FGS ведёт себя иначе, вернуться к отдельной службе.

**Жёсткое ограничение платформы, определяющее дизайн:** `RECORD_AUDIO` —
while-in-use разрешение. Микрофон нельзя открывать до нажатия «Ответить».
Входящий звонок = уведомление `CallStyle` + full-screen intent; захват
звука начинается только из интерактивного действия пользователя.
`canUseFullScreenIntent()` на API 34+ может быть `false` — тогда
показываем обычное heads-up-уведомление и предлагаем
`ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT` в настройках приложения.

### 4.4 Точки врезки в существующий код

* `cloud/CloudSocket.kt`: в `Observer` — `onCallSignal(frame)`; в
  `Connection` — `sendCallFrame(peer, JsonObject)` по образцу
  `sendFileFrame`; в `deliver` — разбор `call-*`. `call-v1` в `CLIENT_CAPS`
  объявляется **только когда локальный движок доступен**.
* `cloud/SyncEngine.kt`: в `Listener` — `onCallSignal(from, frame)`, проброс
  из внутреннего `Observer` рядом с `onWake`/`onTyping`. Не фильтруется
  через `live()`: звонок должен доходить независимо от того, какой разговор
  открыт.
* `cloud/CloudController.kt`: прокидывает сигнал в `CallController` и наружу
  публикует `callState` + действия (`placeCall`/`answerCall`/`declineCall`/
  `hangupCall`/`setCallMuted`/`setCallAudioRoute`/`dismissCall`).
* `ChatService.kt`: реализация нового колбэка `Listener` → `CallController`;
  никаких изменений в promote/demote.
* `cloud/TailchatFirebaseMessagingService.kt`: ветка `kind == "call"` →
  валидация `callId` тем же `validIdentity`, затем маршрут звонка (не
  `ChatService.ACTION_WAKE`: `PushNotificationWorker` тянет сообщение по id,
  звонок не сообщение).
* `cloud/CloudModels.kt`: `CloudUser` += `callable: Boolean` (по умолчанию
  `false` — старый сервер поля не пришлёт), разбор в `CloudSocket.deliver`
  вместе с `online`/`lastSeen`.
* `ui/CloudScreen.kt`: `BarAction` с иконкой телефона в `actions` у
  `CompactBar` — только для реального собеседника (не Saved Messages,
  не AI), только при `call-v1` в серверных капах, `peer.callable == true`
  и работающем локальном движке (см. §9.1).
* Строки: `values/strings.xml` + `values-ru/strings.xml` — паритет
  обязателен (на момент составления плана — ровно по 330 в каждом).

### 4.5 Журнал звонков

`MessageEntity` (`data/Entities.kt`) уже имеет `kind` и `system`, но не
имеет полей звонка, а хранить в `text` локализованную строку нельзя —
язык меняется в рантайме (`AppLocale`). Решение: **новые nullable-колонки**
для исхода и длительности, Room `version = 5 → 6`, схема
`android/app/schemas/.../6.json`, миграция + строка в
`TailchatDatabaseMigrationTest`. Рендер — отдельный компакт-бабл, текст
собирается из ресурсов на месте.

Пропущенный звонок = строка журнала + обычное уведомление в существующем
канале сообщений.

Строка пишется **только локально**: `call-*` принципиально не идут ни в
очередь, ни в историю сервера (§3.1), поэтому каждое устройство одного
аккаунта описывает то, что увидело само, и один `callId` на двух телефонах
может дать разные строки (одно ответило, другое узнало про `call-taken`) —
это не баг.

## 7. Ручные сценарии (без них фаза не закрыта)

1. Оба приложения открыты на этом же разговоре — звонок, разговор, сброс.
2. У вызываемого открыт **другой** разговор — звонок приходит (главная
   причина правки сервера).
3. Приложение вызываемого убито свайпом, экран заблокирован — звонок
   приходит через FCM, ответ с локскрина.
4. Оба в мобильной сети разных операторов (CGNAT) — проверка TURN;
   в logcat видно `relay`-кандидат.
5. Отклонение, «занято» (второй входящий во время разговора), таймаут 45 с
   без ответа → пропущенный в журнале у обеих сторон.
6. Смена сети во время разговора (Wi-Fi → LTE): ICE restart, разговор
   восстанавливается или честно завершается `failed`.
7. Два устройства одного аккаунта: отвечает одно, у второго звонок
   гаснет (`call-taken`).
8. Звонок на аккаунт, который сидит в **web**-клиенте: web должен молча
   игнорировать `call-*`, у звонящего — таймаут, никаких ошибок и
   отключений сокета ни у кого.
9. Разрешение на микрофон отклонено — понятная ошибка, а не тишина.

## 8. Риски

| Риск | Проявление | Ответ |
| --- | --- | --- |
| Размер APK ×3 | self-update тянет 13–16 МБ вместо 5 всем, включая мобильный интернет | принято (§9.1, 32-битные поддерживаются); факт измеряется в фазе 0 и пишется в worklog; >20 МБ — вернуться к владельцу |

| CGNAT без TURN | звонки не соединяются у части людей | TURN в фазе 2, до клиента; при отсутствии — честная ошибка |
| Android 14 FGS/микрофон | `SecurityException` при старте из фона | микрофон только после ответа пользователя (§4.2) |
| `USE_FULL_SCREEN_INTENT` не выдано | звонок не будит экран | `canUseFullScreenIntent()` + heads-up + переход в настройки |

| coturn как открытый прокси | доступ во tailnet/WireGuard хоста | `denied-peer-ip` **плюс** `listening-ip`/`relay-ip` (§3.4) + проверка отказа в приёмке фазы 2 |
| Эхо/громкость на OEM | неюзабельный разговор на части телефонов | HW AEC/NS + `MODE_IN_COMMUNICATION`; проверять минимум на двух разных вендорах |

## 9. Принятые решения (2026-09-15, владелец)

1. **ABI — `arm64-v8a` + `armeabi-v7a`.** 32-битные телефоны поддерживаются.
   Цена: release-APK ~13–16 МБ вместо ~5 (`AppUpdateApi` раздаёт один
   универсальный APK всем). Факт обязан быть измерен в фазе 0 и записан в
   `docs/worklog.md`; если превысит 20 МБ — вернуться с фактом, а не молча
   резать ABI. **По факту получилось 23,3 МБ** — владелец, увидев цифру,
   подтвердил оба ABI (worklog, седьмая часть); решение остаётся в силе.
   На `armeabi-v7a` libwebrtc работает, но это самые слабые устройства из
   поддерживаемых, поэтому: инициализация `PeerConnectionFactory`
   **лениво и в `runCatching`**; если движок не поднялся (любая причина —
   отсутствующая библиотека, OOM, урезанный OEM-образ), кнопка звонка
   скрыта, входящий `call-offer` получает `call-end{reason:"unsupported"}`,
   и приложение продолжает работать как чат. Падать из-за звонков
   приложению нельзя ни на каком устройстве.
   Приёмка фазы 0 включает прогон **release**-APK и на `arm64-v8a`, и на
   `armeabi-v7a`/API 29.
2. **TURN — coturn на том же `ovh`.** Утверждено. 6 CPU / 11 ГБ, релей
   ~40 кбит/с в каждую сторону на звонок; `denied-peer-ip` для tailnet и
   WireGuard обязателен (§3.4).
3. **Видео — не в этой очереди**, но возможно когда-нибудь позже. Практика
   для исполнителя: аудио-звонок реализуется как аудио-звонок, без
   спекулятивных абстракций «под видео»; но и без решений, делающих видео
   невозможным. Конкретно это значит: `media:"audio"` — поле кадра
   `call-offer`, а не константа в коде; `WebRtcEngine` получает список
   треков параметром, а не хардкодит один; `CallScreen` не привязан к
   разметке «только аватар». Ничего сверх этого под видео не делается,
   тестов на видео нет.
4. **Web — не в этой очереди**, но тоже возможен позже. Протокол §2 уже
   клиент-нейтрален (обычные кадры `call-*` через тот же релей), поэтому
   web-очередь later не потребует менять ни сервер, ни Android.
   Пока звонки только в APK, и практическое следствие обязано быть
   отражено в UI: позвонить человеку, сидящему только в web, нельзя — у
   него ничего не зазвонит. Кнопка звонка в Android показывается только
   когда у собеседника есть **живая сессия, объявившая `call-v1`**
   (поле `callable` в ростере, §3.1.6) — иначе кнопка скрыта, вместо
   звонка в пустоту с таймаутом 45 с.

   `versionCode`; `announcedVersion` в боевом `accounts.json` совпадает.

**Что нельзя трогать:**

* promote/demote и `ACTION_GRACE_MS` в `ChatService` — звонок получает
  свою службу (или, как вышло по факту, только читает уже объявленный тип
  FGS), а не переписывает этот жизненный цикл (§4.2).
* Существующие типы кадров и `QUEUEABLE`/`SELF_SYNC` — `call-*` добавляется
  рядом, а не внутрь них (§3.1).
* Ветку `ACTION_WAKE`/`PushNotificationWorker` — звонок идёт своим
  `kind:"call"`, а не через путь «дотянуть сообщение по id» (§4.4).
* Сервисные/анонсные сообщения — только через уже запущенный облачный
  процесс, никогда отдельным процессом по `accounts.json`.

## 3. Модель угроз

Защищает от: чтения переписки по диску/бэкапу/дампу памяти сервера, от
оператора сервера, читающего хранилище, от подмены содержимого сообщения
сервером (сообщение Megolm подписано ключом сессии, а ключ сессии приходит от
устройства-отправителя по Olm).

Не защищает (записать в README при выпуске, не обещать больше):
- **Веб-клиент — код с того же сервера.** `web/cloud/app.js` раздаёт сервер;
  злонамеренный сервер может отдать бандл, который уносит ключи. E2EE в вебе
  не сильнее доверия к серверу, который раздаёт код. Терминал и APK — нет:
  код ставится отдельно (`git clone`, подписанный APK).
- **Реестр устройств ведёт сервер.** Он может дописать собеседнику «устройство».
  Защита — cross-signing (§4.2): чужое устройство без подписи мастер-ключа
  собеседника не получает ключей беседы и видно как предупреждение.
- Метаданные §2; звонки (сигналинг идёт через сервер — `call-*`, вне этапа);
  уже накопленная история (остаётся шифрованием на диске, как сейчас).
- Доступность и порядок: сервер может не доставить, задержать, удалить
  сообщение и подменить внешний `ts` (время на экране — серверное). Подменить
  текст, автора или `id` — не может (§4.3).
- **Открытый текст до первого шифрования.** По политике §1.2 сервер может
  выдавать собеседнику «устройство без ключей» и так держать беседу открытой,
  пока в ней не было ни одного шифрованного сообщения. Защита — только пометка
  «не зашифровано»; после первого шифрованного сообщения откат заметен (§7).
- Устройство Tailik на сервере (§1.1): беседы, ключи которых получает Tailik,
  читаемы процессом на сервере. Это следствие решения, а не дыра; ключи —
  только в беседах, где Tailik включён, и собеседник это видит (§1.2).

## 4. Протокол

Модель Matrix (её и реализует vodozemac), сужена до бесед один-на-один.
Групп в Tailchat нет (`hub.js` — только пары логинов).

### 4.1 Устройство

- Устройство = одна установка клиента: свой `olm::Account` (Curve25519 +
  Ed25519), `deviceId`, выдаётся сервером при входе. Токен привязан к
  устройству: сейчас запись токена — только `{login, createdAt, lastUsed}`
  (`accounts.js:1046`), появится `deviceId`. Отзыв токена = удаление
  устройства = ротация ключей бесед у собеседников.
- Имеющийся `pubKey` аккаунта (`accounts.js:1110,1160`, Ed25519 из
  `src/identity.js`, подписан сертификатом сервера) — **один на аккаунт и
  перезаписывается каждым входом**. Для E2EE не годится и не переиспользуется;
  остаётся LAN-идентичностью терминала.
- Одноразовые ключи (OTK): устройство держит на сервере до 50 + fallback-ключ
  (`Account::generate_one_time_keys`, `generate_fallback_key`,
  `mark_keys_as_published` — API 0.11.1 сверен по docs.rs). Забирать OTK
  (`keys/claim`) может только друг или сам аккаунт, не чаще 10 в минуту на
  пару; иначе любой исчерпает их и сведёт первые сообщения к fallback-ключу.
- **Ключи устройства неизменны.** Сервер отвергает загрузку других identity
  keys под существующим `deviceId`; клиент, увидевший другие ключи под
  знакомым `deviceId`, считает это новым недоверенным устройством с
  предупреждением, а не обновлением.
- **Класс устройства** — поле `kind: "client" | "assistant"` внутри
  подписанных ключей устройства (не в ростере и не в отдельном поле сервера).
  `assistant` — устройство Tailik (§6): по умолчанию ключей не получает.
- **Старые токены.** Токены не истекают (`accounts.js:1299-1324`, `lastUsed`
  с точностью до минуты), их у аккаунта может быть много с одной установки.
  Токен без `deviceId` считается «устройством без ключей» (и держит беседу
  открытой, §7), только если `lastUsed` моложе 30 суток [предложение]; более
  старый — не учитывается, а вернувшийся клиент увидит заглушку §5.

### 4.2 Аккаунт: cross-signing

- Мастер-ключ аккаунта (Ed25519) подписывает ключ самоподписи, тот —
  устройства аккаунта. TOFU и QR сверяют **мастер-ключ**, не каждое
  устройство: новое устройство собеседника, подписанное его мастер-ключом,
  доверено без вопросов; неподписанное — ключей не получает, в беседе
  предупреждение.
- Смена мастер-ключа собеседника — заметное предупреждение (§1.1), отправка в
  беседу останавливается до подтверждения человеком. Ревью: оставить — сервер
  этим может только помешать отправке, но не прочитать.
- Ключи сессий Megolm пересылаются (запрос «ждём ключ», §4.3) **только между
  своими устройствами, подписанными ключом самоподписи**, и только сессий
  бесед этого же аккаунта. Пересланный или восстановленный из бэкапа ключ
  (`InboundGroupSession::import`, без подписи сессии) помечается «отправитель
  не подтверждён» и подтверждается, только когда придёт исходный `SessionKey`.
- Новое своё устройство подписывается одним из способов: QR со старого
  устройства или секрет бэкапа (§4.5), где лежит закрытый ключ самоподписи.
- Где камеры нет (терминал↔терминал, десктоп-веб) — сравнение эмодзи/чисел
  (`vodozemac::sas`); и сверка собеседника, и подпись своего устройства (§1.2).
  vodozemac даёт только примитив: обмен с обязательством (принимающий шлёт
  хэш своего ключа до того, как увидит чужой — иначе MITM подбирает
  совпадающие эмодзи) делает протокол поверх, по образцу `m.sas.v1`. MAC —
  только `calculate_mac`/`verify_mac`; устаревший
  `calculate_mac_invalid_base64` не используется. В MAC входят оба
  мастер-ключа и ключи устройств, в `info` — оба логина и `deviceId`.
- Подписи — `Account::sign` / `Ed25519PublicKey::verify` vodozemac; формат
  подписываемого — канонический JSON (тот же приём, что `canonicalJson` в
  `src/identity.js`), фиксируется тестовыми векторами.

### 4.3 Сообщения

- На каждую беседу и каждое устройство-отправитель — исходящая сессия Megolm
  (`megolm::GroupSession`). Ключ сессии раздаётся Olm-сообщением (to-device)
  каждому доверенному устройству собеседника **и своим** остальным
  устройствам (сейчас они получают копию через `self: true`,
  `hub.js:18-20`). Новому устройству отдаётся ключ с **текущего** индекса
  (`GroupSession::session_key`): прошлое — только через бэкап (§4.5).
- **Привязка входящей сессии.** Получив `SessionKey` по Olm, устройство
  записывает, от кого он: логин, `deviceId`, Ed25519 и Curve25519
  отправителя (из проверенного Olm, §4.4) и беседу. Поля `dev`/`sid` конверта
  — только подсказка для поиска, сервер может их менять. Расшифровка
  отвергается (`Undecryptable`, строка хранится), если сессия пришла не от
  внешнего `from` этого сообщения или из другой беседы.
- Ротация: после 100 сообщений, через 7 суток, при удалении любого устройства
  из списка любой стороны, при смене доверия.
- Конверт вместо `text`/`image`/`voice`/`replyTo`:

```json
{"t":"msg","id":"m-…","e2ee":{"v":1,"dev":"<deviceId>","sid":"<megolm session id>","ct":"<base64>"}}
```

  Внутри `ct` — прежний `d` без `t` (`text`, `replyTo`, `image`, `voice`,
  `linkPreview`, `buttons`) **плюс** `from`, `to`, `id` и `kind`
  (`msg`/`edit`/`forward`). После расшифровки они обязаны совпасть с внешними
  — иначе `Undecryptable`: сервер не может переложить шифротекст в другую
  беседу, под другой `id` или выдать правку за сообщение. `id` и `ts` остаются
  и снаружи: на них стоят идемпотентность сервера, лента и лестница меток
  (§12 `AGENTS.md`).
- **Повтор индекса.** Устройство хранит `(sid, message_index) → id`. Тот же
  индекс под другим `id` — повтор сервером, отвергается.
- **Один конверт на сообщение.** Шифрование и выбор «шифровать или открыто»
  — один раз, при первой выдаче из очереди; конверт ложится в строку очереди
  в том же Persist, что и продвижение храповика. Каждый повтор шлёт те же
  байты: иначе новый индекс дал бы другой конверт, `sameMessage` сервера —
  `message_id_conflict` и ⚠ у доставленного сообщения, а каждый повтор сжигал
  бы индекс.
- Правка (`kind: edit`) принимается, только если её сессия принадлежит тому же
  аккаунту, что и исходное сообщение. Цитата ответа рисуется из своей копии
  сообщения по `replyTo.id`, а не из текста, который прислал отправитель.
- Вложения — пока внутри того же `ct`. Лимит кадра — `CLOUD_FRAME_MAX_CHARS`
  = 10 МиБ base64 + 1 КиБ (`limits.js:4-5`, проверка `hub.js:1670`). Если
  положить в `ct` прежний `dataUrl` (уже base64), шифротекст в base64 вырастет
  в 4/3 раза — ~13,3 МиБ, больше лимита. Поэтому внутренний формат двоичный:
  заголовок JSON + сырые байты вложения; тогда `ct` ≈ прежнему `dataUrl`
  плюс MAC и подпись Megolm. Для кадров с `e2ee` лимит сервера получает запас
  на этот хвост, `MAX_OUTBOUND` ядра (`frames.rs`, зеркало лимита сервера) —
  тот же; `MAX_INBOUND` = 4 × `MAX_OUTBOUND` запас уже имеет. Пересекается со спекой
  `2026-11-03-history-media-refs.md`: её `{mime,size,width,height}` сервер при
  E2EE не знает; ссылка `(peer,id,slot)` остаётся, описание уходит внутрь
  конверта. Вынос в зашифрованные блобы — отдельно, вне этапа.
- **Форма вложения зависит от читателя (R34, 2026-11-15).** Двоичная форма
  (`image:{mime,width,height}` / `voice:{mime,duration,waveform}` в заголовке +
  байты после него) ушла в прод в 1.147; ядро ≤ 1.147 её не читает — читает
  заголовок как тело, `dataUrl` нет, остаётся подпись, а ack всё равно уходит
  (✓✓ над потерянным фото). Поэтому устройство объявляет, что умеет:
  `keys/upload` несёт `caps` рядом с `deviceKeys` (не подписано, как `name`;
  сервер нормализует, хранит, отдаёт в `keys/query`, меняет список —
  `device-list-changed`). `e2ee-blob-v1` — «читаю двоичную форму». Отправитель
  кладёт байты, только если **все** получатели (устройства собеседника и свои)
  объявили `e2ee-blob-v1`; иначе — прежний `dataUrl` внутри `ct`, который
  читает любое ядро. Встроенная форма на треть больше: если она не влезает в
  `MAX_SEALED`, сообщение падает до провода с `ServerError{code:"peer_outdated"}`
  (⚠, строка остаётся для «повторить»; клиенты пишут «у собеседника старая
  версия — попросите обновить»). Ядро, получившее вложение, которое оно не
  может восстановить (неизвестная будущая форма), ставит `mediaDropped` и
  **не шлёт ack** за это сообщение (ватермарка: более позднее читаемое
  сообщение её всё равно поднимет). Сервер — не авторитет формы: подменив
  `caps`, он может лишь сделать вложение встроенным (оно всё равно внутри
  `ct`) или вызвать отказ — не прочитать.
- Не расшифровалось (нет ключа сессии) — строка «ждём ключ» и запрос ключа у
  своих устройств; после 24 ч — «не удалось расшифровать». Никогда не
  показывать пусто и не отбрасывать: строка в хранилище с конвертом, повторная
  попытка при приходе ключа. Вложения внутри `ct` защищены MAC и подписью
  Megolm вместе с текстом — отдельной схемы шифрования вложений нет.

### 4.4 To-device: доставка ключей

Новый долговечный канал сервера — очередь **на устройство**, не на аккаунт:
- `{k:"to-device", to:<login>, device:<id>, body}` от клиента;
  `{k:"to-device", from, fromDevice, seq, body}` к клиенту;
  `{k:"to-device-ack", seq}` — **после** Persist (контракт этапа 3: `ack`
  только после того, как строка на диске). Сервер хранит до ack, лимит на
  устройство.
- Устройство не в сети — ждёт в очереди; в push не уходит.
- **Внутри Olm-сообщения** — логины и Ed25519 отправителя и получателя;
  получатель проверяет, что это он и что ключ отправителя — ключ устройства,
  от которого пришло сообщение. Иначе сервер перенаправит чужое
  Olm-сообщение.
- Входящее prekey-сообщение расходует OTK (`create_inbound_session`):
  аккаунт и новая сессия — в одном Persist до `to-device-ack`. Упали раньше —
  сервер передоставит, OTK в сохранённом аккаунте ещё есть.
- Сессия Olm не расшифровывается («заклинило», например после
  восстановления старого состояния) — новая сессия через свежий OTK, не чаще
  раза в час на пару устройств.
- Лимит очереди — и на устройство, и на отправителя (≤ 100 от одного
  устройства): один друг не должен забить очередь и задержать чужие ключи.

### 4.5 Бэкап ключей

- Сервер хранит зашифрованные ключи входящих сессий Megolm
  (`export_at_first_known_index`), закрытые ключом бэкапа. Шифрование —
  AES-256-GCM (RustCrypto `aes-gcm`), случайный 96-битный nonce на запись,
  AAD = `(login, sid, версия бэкапа)`: сервер не переставит записи между
  сессиями. Не свой примитив, но и не vodozemac: libolm-совместимое
  `PkEncryption` vodozemac держит под флагом `insecure-pk-encryption` — не
  используется. Ключ бэкапа держит каждое подписанное своё устройство (в
  SQLCipher) и получает его по Olm от другого своего устройства или из
  секрета.
- Ключ восстановления — 256 случайных бит с устройства, без KDF. **Фраза
  перебирается сервером офлайн** (бэкап у него): Argon2id (64 МиБ, t = 3),
  соль у сервера, минимум — 4 слова или 16 символов [предложение]; UI прямо
  говорит, что ключ сильнее фразы. Argon2id — не в `Core::handle` (секунда
  CPU и 64 МиБ), а в драйвере по явной команде.
- В том же хранилище секретов, закрытый тем же ключом, лежит закрытый ключ
  самоподписи (§4.2): им новое своё устройство подписывает себя.
- **Секрет бэкапа не может быть паролем аккаунта, дополнительным паролем или
  нынешним ключом восстановления**: пароль сервер получает открыто при входе
  (`accounts.js:1122`, scrypt на сервере), ключ восстановления сервер сам
  генерирует и хэширует (`accounts.js:1093-1095`). Любой ключ из них сервер
  может вычислить. Решение (§1.2): ключ восстановления, созданный на
  устройстве и показанный один раз, + необязательная фраза.

## 6. Ядро

- Новый крейт **`tailchat-crypto`**: обёртка vodozemac — аккаунт, сессии Olm,
  Megolm, cross-signing, бэкап. Его вызывает `Core::handle`; наружу ядро не
  отдаёт ни одного типа vodozemac (napi-rs/UniFFI/WASM видят только свои типы).
- **Случайность.** Ядро сейчас без случайности (§2 спеки ядра). vodozemac берёт
  её из ОС сам: `Account::new()` и `GroupSession::new(config)` параметра
  источника не принимают (API 0.11.1, docs.rs). Решение: исключение
  записывается в §2 спеки ядра — недетерминированы только байты шифротекста и
  ключей; тесты проверяют расшифрованный смысл, а не байты.
- **Persist до Send — для храповика тоже.** Продвижение исходящей сессии
  Megolm/Olm идёт в тот же `Output::Persist`, что и строка сообщения, до
  `Output::Send`. Иначе падение между отправкой и записью повторит индекс
  Megolm (тот же ключ и IV для другого текста). Входящее: состояние сессии и
  расшифрованная строка — в одном Persist до `ack`. Это существующие контракты
  этапов 2–3, ничего нового в порядке.
- Новые `StoreOp`: аккаунт, сессии Olm, входящие/исходящие Megolm, привязка
  сессий (§4.3), `(sid, index) → id`, устройства и доверие собеседников,
  очередь to-device, флаг «беседа шифровалась» (§7). Отдельного ключа пикла
  нет: пиклы лежат в SQLCipher, второй ключ, выведенный из того же ключа
  устройства, ничего не добавил бы. Секреты в `StoreOp` — `Zeroizing`, их
  `Debug` печатает `[redacted]` (сейчас `StoreOp` — `derive(Debug)`, текст
  он уже печатает, ключи не должен). `MemStore` и
  `tailchat-store/tests/conformance.rs` меняются вместе (эталон —
  `tests/common/mod.rs`).
- Устройство `assistant` (Tailik) получает ключи беседы, только если владелец
  включил его в ней. Включение — шифрованное служебное сообщение владельца в
  самой беседе (не флаг сервера): по нему клиент собеседника добавляет Tailik
  в получатели и показывает «Tailik читает эту беседу»; выключение —
  такое же сообщение и ротация сессии.
- Новые `Event`: `Undecryptable{peer,id}`, `KeyChanged{peer}`,
  `UnverifiedDevice{peer,device}`, `EncryptionState{peer, on}`.
- Новые `Input`: ответы `keys/query`/`claim` (через имеющийся `Fetch`, как
  история), `to-device`.

## 7. Совместимость

- Шифровать беседу можно, только если **все** устройства обеих сторон
  объявили ключи. У каждого сегодня есть веб или APK, которые ключей не
  объявят до этапа 7 — по решению §1.2 зашифрованных бесед у людей до этапа 7
  не появится; этап 6 проверяется на временных аккаунтах.
- Смешанный режим (§1.2): пока не готовы все устройства — открыто с пометкой
  «не зашифровано» во всех клиентах, где беседа рисуется. Беседа, в которой уже
  было шифрованное сообщение, помнит это (долговечный флаг на устройстве):
  открытый текст в ней своё устройство не отправит без явного подтверждения
  человека, входящий открытый текст показывается с предупреждением.
- **Бот — не флаг сервера.** Сейчас ботом аккаунт объявляет себя сам
  (`hello` с `v:'bot'`, `hub.js:1705` → `markBot`, `accounts.js:2861`), и
  ростер от сервера. Если бы «бот» отключал шифрование, сервер выключил бы
  его любому человеку. Поэтому решает только §7 выше: у бота нет
  опубликованного мастер-ключа — беседа открыта сама. Флаг бота меняет лишь
  текст пометки («бот — без шифрования» вместо «не зашифровано»). Аккаунт с
  мастер-ключом флаг бота не делает открытым.
- Старая история не перешифровывается: она уже на сервере в открытом для
  процесса виде (шифрование на диске). Удаление — отдельное решение, вне этапа.

### 8.1 Контракт подэтапа 6a (реализован)

Код: `src/cloud/e2ee.js` (проверки формы, константы, `frameForCaps`),
`accounts.js` (`state.e2ee`, журнал, `e2ee*`), `hub.js`, `server.js`,
`limits.js` (`CLOUD_E2EE_FRAME_MAX_CHARS` = лимит кадра + 16 КиБ).

HTTP (bearer; тело до 64 КиБ только у `upload`):
- `POST /api/e2ee/keys/upload` `{deviceKeys?, name?, oneTimeKeys?, fallbackKey?,
  crossSigning?, replaceCrossSigning?, password?}` → `{deviceId, registered,
  oneTimeKeyCount, fallbackKey}`.
  Первый вызов сессии выдаёт `deviceId` (16 знаков base64url) и привязывает его к
  токену; `deviceKeys` обязаны назвать `login` и этот `deviceId`, `kind` —
  `client`/`assistant`, `keys.curve25519`/`ed25519` — 43 знака base64 без `=`.
  Отказы: `invalid_*` (400), `device_required` (400), `device_keys_changed`,
  `device_limit`, `one_time_key_conflict`, `one_time_key_limit` (409); в ответе
  об ошибке — `deviceId`. Подписи сервер хранит как есть и не проверяет.
  **Замена ключей аккаунта** (2026-11-10): `crossSigning` при уже опубликованном
  `master` без `replaceCrossSigning: true` молча игнорируется (как и было); с
  флагом — требует основной `password` аккаунта (проверяется до очереди E2EE тем
  же хешем, что вход) и **полный набор** `master` + `selfSigning`. Отказы:
  `bad_credentials` — **403**, не 401 (401 на этом маршруте значит «токен
  недействителен», клиент на него выходит из аккаунта); перебор — общий с
  `/api/login` ограничитель по адресу → 429 `too_many_attempts`; половина набора —
  400 `invalid_cross_signing`. Первая публикация ключей пароля не требует.
  Успех рассылает друзьям `device-list-changed`.
- `POST /api/e2ee/keys/query` `{logins}` (≤ 50) → `{users: {login:
  {crossSigning, devices: {id: {deviceKeys, name, createdAt}}, legacySessions}}}`
  — только сам аккаунт и друзья. `legacySessions` — токены без
  зарегистрированного устройства с `lastUsed` моложе 30 суток.
- `POST /api/e2ee/keys/claim` `{claims: {login: [deviceId]}}` → `{keys: {login:
  {id: {keyId, key, fallback}}}, rateLimited}`; OTK выдаётся один раз, затем
  fallback; ≤ 10 в минуту на пару аккаунтов, ≤ 50 за запрос.
- `/api/history?…&e2ee=1` — конверты; без параметра — заглушка вместо них.
- `logout` удаляет устройство сессии; `register`/`login`/`recover`/`logout` и
  изменение устройства или cross-signing шлют `{k:"device-list-changed",
  login}` сессиям с `e2ee-v1` этого аккаунта и его друзей.

WebSocket (только для `auth` с `caps: ["e2ee-v1"]`; сервер объявляет cap в
`ready`):
- `{k:"to-device", id?, to, device, body}` (тело ≤ 64 КиБ, входит в бюджет
  кадров) → `{k:"to-device-accepted", id, seq}` только после fsync журнала;
  получателю — `{k:"to-device", seq, from, fromDevice, body, at}` живьём и после
  каждого `ready`, пока он не пришлёт `{k:"to-device-ack", seq}` (накопительно).
  Отказы — `{k:"error", code, id}`: `device_required`, `device_not_found`,
  `peer_not_found`, `blocked`, `invalid_to_device`, `to_device_full`,
  `store_failed`; без cap — `unknown_action`, как раньше.
- `msg`/`ai` с `e2ee: {v:1, dev, sid, ct}`: `dev` обязан быть устройством этой
  сессии, рядом нельзя `text`/вложения/`replyTo`/`forwardedFrom`/`buttons`/
  `linkPreview` — иначе `{k:"error", code:"bad_envelope", peer, id}`. Повтор с
  тем же конвертом — `message-accepted`, с другим — `message_id_conflict`.
  Сессии без cap (живьём, self-sync, очередь, `message-event` веба) получают
  `text` = заглушка без `e2ee`; превью ростера — заглушка + `encrypted: true`;
  push — «New message» (`pushPreview` без текста).
- Конверт > 64 КиБ считается вложением в бюджетах медиа и при вытеснении уходит
  целиком (текст внутри него).

Хранение: все мутации E2EE — строки журнала (`e2ee-upload`, `-claim`, `-send`,
`-ack`, `-remove`) с номером из общего счётчика; применение идемпотентно по
водяным знакам (`keysSeq`, `crossSeq`, `ackedThrough`, `removed`) — повтор
строки журнала поверх более нового снимка не возвращает выданный OTK и
подтверждённое сообщение.

Отклонения от §5, решено при реализации: `/backup` — в 6e вместе с самим
бэкапом; правка шифрованного сообщения — в 6c (сейчас `edit` несёт только
открытый текст); `lastSeen` устройства не хранится (`createdAt` и
`legacySessions` хватает политике §7).

Пределы (существовали до 6a, не изменены): аккаунты, токены и офлайн-очередь
пишутся только снимком (≥ 1 с после изменения) — падение раньше теряет новую
регистрацию/вход и очередь, но не историю и не журнал E2EE. Привязка
`deviceId` к токену восстанавливается из строки `e2ee-upload`, если токен
пережил падение.

### 8.2 Контракт подэтапа 6b (реализован)

Крейт `crates/tailchat-crypto` (vodozemac `=0.11.1` без `libolm-compat`).
Наружу — только свои типы; `Err` (`CryptoError`) — только ошибка вызывающего,
битое хранилище или ключи от сервера, которые не прошли проверку; всё, что не
читается в пути расшифровки, — `Undecryptable`.

- **Подпись** (§11 «открыто» закрыто): байты — `canonicalJson` из
  `src/identity.js` (ключи по UTF-16, экранирование `JSON.stringify`) объекта
  без верхних `signatures` и `unsigned`; целые только в ±(2⁵³ − 1), дробные —
  `NotCanonical`. Подпись — `signatures: {login: {"ed25519:<deviceId>":
  base64}}`. Векторы — `tests/fixtures/signing-vectors.json`, сделаны
  `node:crypto` из того же `canonicalJson`, Rust сверяет байты и подпись.
- **`DeviceKeys::from_json`** — форма §8.1 + самоподпись; ключ принимается
  только в каноническом написании (одна строка на ключ). Совпадение `login` и
  `deviceId` с тем, под чем сервер его выдал, сверяет ядро (6c).
- **`Account`**: `upload_body()` — тело `keys/upload` (`deviceKeys`,
  `oneTimeKeys`, `fallbackKey`, каждый ключ подписан устройством, OTK ≤ 50),
  `mark_keys_as_published()` — после ответа сервера.
- **`OlmChannel`** (Olm v1 — v2 у vodozemac только за
  `experimental-session-config`): `start_session` проверяет подпись
  заявленного OTK; тело `to-device` — `{v:1, type, ct}`; открытый текст
  называет `sender`/`senderDevice`/`senderKey` и `recipient`/
  `recipientDevice`/`recipientKey`, расшифровка сверяет обе стороны
  (`WrongSender`/`WrongRecipient`). До 8 сессий на устройство, новые вперёд.
  Pre-key расходует OTK аккаунта — аккаунт и канал в одном Persist.
- **`OutboundGroup`/`InboundGroup`** (Megolm v1): `create` даёт и входящую
  половину для своих же сообщений. `room_key()` — с текущего индекса;
  `ReceivedRoomKey` делает только `OlmChannel::decrypt`, поэтому входящая
  сессия всегда привязана к проверенному устройству и беседе; ключ беседы, в
  которой нет своего логина или логина отправителя, — `WrongConversation`.
  Ротация `rotation_due`: 100 сообщений, 7 суток, устройство пропало из
  получателей (или его ключи сменились — `unshared` считает его новым);
  смену доверия решает вызывающий. Кого включать в получатели (Tailik) —
  тоже вызывающий (6c/6d).
- **Открытый текст конверта**: `[1][u32 BE длина][JSON][байты вложения]`;
  в JSON — прежний `d` плюс `from`/`to`/`id`/`kind` (`msg`/`edit`/`forward`),
  содержимое с этими полями — `ReservedField`. Расшифровка сверяет `sid`/`dev`
  с сессией (`SessionMismatch`), отправителя и беседу сессии, затем поля
  внутри с кадром (`FieldMismatch`), правку — с автором исходного
  (`EditByOtherAccount`), индекс — с уже виденным `id` (`Replay`). Тот же
  конверт повторно читается снова (история, переподключение).
- **Хранение**: у каждого объекта с секретом `pickle()` — `Zeroizing` JSON
  `{v:1, p}` (без отдельного ключа, §6), ошибка разбора без текста (сообщение
  парсера могло бы процитировать ключ). `Debug` секретов не печатает.

Пределы, известные и оставленные: `(sid, index) → id` лежит внутри пикла
входящей сессии и не ограничен (6c может вынести его в свой `StoreOp`);
повтор **старой правки** с тем же индексом проходит как идемпотентный —
применять правку ядро должно по наибольшему `index`; промежуточные буферы
`serde_json` не стираются; pre-key с неверными полями отправителя всё равно
расходует OTK (сообщение подлинно от владельца ключа устройства).

    сохранён), собеседник попадает в `key_changed`: один раз выдаётся
    `Event::KeyChanged {peer}`, а `decide(peer)` возвращает `Wait` — исходящие
    сообщения удерживаются без расхода попыток и без холостого таймера до
    `Action::AcceptPeerKey {peer}` или сверки по QR/SAS, которые сбрасывают

    запись в каталоге **или** закреплённый мастер-ключ: каталог живёт в памяти
    и после перезапуска пуст, а `peer_identities` возвращаются из хранилища.
    Чужие аккаунты, с которыми не было дела, по уведомлению не запрашиваются.

- **SAS (`SasSession`, `SasMessage`, `SAS_EMOJIS`) и QR (`QrVerification`)**:
  - Четырёхшаговый обмен поверх Olm (`ToDevice::Sas`): `Start` →
    `Accept {commitment}` (SHA-256 от `transaction_id`, обоих логинов/устройств
    и эфемерного ключа принимающего до отправки ключа инициатора) →
    `Key` (инициатор) → `Key` (принимающий, сверяется с `commitment`; при
    пропуске `Accept` — `SasWithoutCommitment`, при несовпадении —
    `SasCommitmentMismatch`) → `Event::SasCodeReady` (7 индексов эмодзи +
    3 десятичных числа) → `Action::ConfirmSas` → `Mac` через
    `EstablishedSas::calculate_mac`/`verify_mac` (в `input` — оба мастер-ключа
    и ключи обоих устройств, в `info` — оба логина, оба `deviceId` и
    `transaction_id`).
  - `Core::qr_verification()` кодирует `tailchat-verify:v1:<login>:<device>:<ed25519>:<master>`;
    `Action::VerifyWithQr` сверяет собеседника (`verified: true`) или своё
    второе устройство.
  - После успешной сверки своего второго устройства авторитетное устройство
    пересылает ему `ToDevice::CrossSigningKey` по Olm; второе устройство
    проверяет `CrossSigning::from_shared`, подписывает свои `deviceKeys`
    ключом самоподписи и публикует их через `keys/upload`.
- **Пересылка ключей сессий (`RoomKeyRequest` / `ForwardedRoomKey`)**:
  - Кросс-подписанное устройство со строками `Sealed {waiting: true}` запрашивает
    недостающие сессии у других кросс-подписанных устройств своего аккаунта.
  - `InboundGroup::export_forwarded` отдаёт `ExportedSessionKey` только
    клиентскому устройству **своего же аккаунта**, подписанному `own_cross`,
    и только для беседы со своим участием (`UntrustedDevice`/`WrongSession`
    во всех остальных случаях).
  - `InboundGroup::from_forwarded_key` импортирует ключ с
    `is_sender_verified() == false`; при приходе прямого `RoomKey`
    `InboundGroup::merge` подтверждает связанность храповика и поднимает

    Argon2id (`m = 64 МиБ = 65536 КиБ`, `t = 3`, `p = 1`, 128-битная случайная
    соль) выполняется вне `Core::handle` (тип `BackupPassphraseKey` создаётся в
    драйвере до передачи `Input::Action`). Ключ фразы оборачивает `BackupKey`
    через AES-256-GCM с 96-битным nonce и `AAD = {"kind":"passphrase","login":…,"version":…}`
    (`PassphraseSlot`).
  - Запись ключа самоподписи (`encrypt_cross_signing` / `decrypt_cross_signing`):
    шифрует `{public, selfSigningSecret}` через AES-256-GCM с 96-битным nonce и
    `AAD = {"kind":"self_signing","login":…,"version":…}`; при расшифровке
    сверяется с опубликованным `CrossSigningPublic` аккаунта.
  - Запись сессии Megolm (`encrypt_session` / `decrypt_session`): экспортирует
    входящую сессию с `first_known_index` (`export_at_first_known_index`),
    шифрует через AES-256-GCM со случайным 96-битным nonce и каноническим
    `AAD = {"login": login, "sid": sid, "version": version}` (§4.5). При
    восстановлении сессия помечается `is_sender_verified() == false` до прихода
    прямого `SessionKey` (§4.2).
  - Передача `BackupKey` между своими устройствами по Olm (`ToDevice::BackupKey` /
    `Received::BackupKey`, `BackupKey::share` / `from_shared`): только между
    клиентскими устройствами своего аккаунта, подписанными `own_cross`;
    отправляется автоматически при QR/SAS-сверке второго устройства и при
    создании бэкапа.
- **Сервер (`POST /api/e2ee/backup`)**:
  - Хранит в `state.e2ee[login].backup` `{version, seq, crossSigning, passphrase,
    sessions}` (до 5000 сессий на аккаунт, до 100 за запрос); мутации пишутся в
    журнал (`kind: "e2ee-backup"`) и идемпотентны по водяному знаку `backup.seq`.
  - Для существующей сессии `sid` новая запись принимается только при строго
    меньшем `firstKnownIndex` (`item.firstKnownIndex < existing.firstKnownIndex`),
    чтобы более поздний индекс не затёр ранний.
- **Ядро и хранилище (`tailchat-core`, `tailchat-store`)**:
  - `StoreOp::PutBackupKey(Secret)` (таблица `backup_key` схемы 3,
    `Snapshot.backup_key`), `ApiCall::Backup`, действия `CreateBackup`,
    `FetchBackup`, `RestoreBackupWithRecoveryKey`, `RestoreBackupWithPassphrase`,
    события `BackupCreated`, `BackupInfo`, `BackupRestored`.
  - При `CreateBackup` пикл `BackupKey` сохраняется в `Persist` до `Output::Post`;
    новые входящие сессии автоматически догружаются в бэкап в `seal_due`.
  - При восстановлении на новом устройстве ядро расшифровывает `CrossSigning`,
    подписывает собственные `deviceKeys` ключом самоподписи (перезагружая их в
    `keys/upload`), импортирует все сессии из бэкапа и сразу вскрывает ожидающие
    строки (`StoreOp::Unseal` + `Event::MessageStored`).

- **`/verify [логин]`** (с 1.146, §8.9) — для **чужого** аккаунта (и без аргумента —
  для открытой беседы) показывает код безопасности, тот же путь, что `/safety`; никакое

  спрашивает `POST /api/e2ee/keys/query` и выбирает устройства, кроме своего

  устройство — ровно то, для чего его сверяют), с неподписанного — только подписанные

  наличию подписи `ed25519:<selfSigning>` в `deviceKeys.signatures` и отсутствию
  `core-unverified-device` по устройству. До 1.146 `/verify` запускал SAS и с чужим
  аккаунтом (только с его подписанными устройствами).
- **`/verify yes` | `/verify no`** — ответ на то, что ждёт ответа: на окно SAS (7 эмодзи
  + 3 числа; в том числе на SAS, который начал собеседник со старого клиента) или на
  показанный код безопасности (`yes` — `confirmSafetyCode` ровно показанного ключа, `no` —
  ничего не отмечается, `e2ee.safetyDiffer`). Ответом считаются, только пока что-то ждёт
  ответа; иначе `e2ee.nothingWaiting` и ничего в ядро.
- **`/trust`** — `acceptPeerKey` открытой беседы, **только** после
  `core-key-changed` для неё и до сверки (`core-device-verified` гасит смену,
  как и само ядро). Иначе `e2ee.nothingToTrust` и ничего в ядро: `AcceptPeerKey`
  перезаписывает личность собеседника как `verified: false`
  (`engine/keys.rs` `accept_peer_key`), и `/trust` без смены ключа снял бы уже
  сделанную сверку.
- **`/backup create`** — бэкап **без фразы**; ключ восстановления показывается
  один раз отдельной строкой с отступом, только на экране (`ui.addLine` ничего
  не пишет на диск, команда не входит в `AI_SAFE_COMMANDS`). **`/backup status`**
  — версия и число сессий, ключ не печатается никогда.
- **`/backup restore`** (2026-11-10) — восстановление на этом устройстве.
  Секрет **никогда не аргумент команды**: он остался бы на экране и в истории
  ввода. Порядок: `fetchBackup` → по `core-backup-info` (версия `0` —
  `e2ee.backupNone`, ничего не спрашивается) открывается **скрытый ввод**
  `ui.promptSecret` — карточка поверх экрана, вместо текста точки (длиннее 32 —
  точки и длина), Enter — отдать, Esc — отменить (`null`, в ядро ничего),
  Ctrl+U/⌘U — стереть; вставка (bracketed paste) идёт в карточку одной строкой,
  не в композер. Клавиши — тем же единственным путём, что и экран блокировки
  (`screen.program.on('keypress')`, AGENTS §1–2); заставка поверх открытой
  карточки не встаёт. Введённое начинается с `tailchat-backup:` →
  `restoreBackupWithRecoveryKey`; иначе — фраза, и только если у бэкапа есть
  слот фразы (`passphraseSalt`), иначе `e2ee.restoreNotAKey`. Отказ ядра
  приходит как `bad-frame` (`try_complete_restore`): `core-link.js` отдаёт его
  событием `core-bad-frame`, а команда говорит о нём, **только пока ждёт
  восстановления** и только о бэкапе (`restoreFailureKey`: неверный
  ключ/фраза и ключ от бэкапа до сброса — `e2ee.restoreWrongKey`, ключ старой
  версии — `e2ee.restoreOldKey`). Без ответа 30 с — `e2ee.restoreNoAnswer`
  (ядро молчит, если устройство не зарегистрировано). Успех —
  `e2ee.backupRestored`. Без скрытого ввода (headless) — `e2ee.restoreNeedsTerminal`.
  **Бэкап возвращает и подпись, не только историю:** `try_complete_restore`
  расшифровывает `crossSigning` бэкапа, сверяя с публичным ключом каталога, и
  ставит его в учётку; следующая загрузка ключей подписывает устройство
  ключом самоподписи аккаунта. Проверено вживую: устройство после нового входа,
  подписанное своим ключом, после `/backup restore` подписано опубликованным и
  читает E2EE-сообщения собеседника.
  Создание бэкапа **с фразой** терминал по-прежнему не предлагает.
- **`/keys reset`** (2026-11-10) — новые ключи аккаунта, когда ключей нет ни на
  одном своём устройстве и `/backup restore` невозможен. Терминал сначала
  предупреждает, что изменится для других, затем открывает ту же скрытую
  карточку (`⚠ СБРОС КЛЮЧЕЙ ШИФРОВАНИЯ`) для **пароля аккаунта** — она и есть шаг
  подтверждения, Esc ничего не меняет. Ядро (`Action::ResetCrossSigning
  { password }`, `engine/e2ee.rs` `reset_cross_signing`): `CrossSigning::new`,
  тело `upload_body_with(Some(&new), true)` — `deviceKeys` этого устройства уже
  подписаны новым ключом самоподписи — плюс `replaceCrossSigning: true` и
  `password`, в слоте `upload`. **Локально ничего не меняется до ответа:** 200 →
  `apply_reset` (ключи в учётку, `PutCryptoAccount`, свой каталог заново,
  `needs_reupload`) → `Event::CrossSigningReset`; 403/429/401/иной статус →
  `Event::CrossSigningResetFailed { bad_password | too_many_attempts |
  signed_out | refused }`, старые ключи в силе. **Нет ответа** (сеть, или сокет
  сменился и `connected()` бросил загрузку) — сервер мог принять: сброс
  остаётся «под сомнением» (`PendingReset.in_doubt`), свой аккаунт ставится в
  `wanted`, и следующий `keys/query` решает (`settle_reset`): публикуется новый
  мастер-ключ — применить, иначе `connection_lost`. Без этого принятый сервером
  сброс с потерянным ответом оставил бы устройство со старым ключом, а новые
  закрытые ключи — нигде. `not_ready` (не зарегистрировано) и `busy` (идёт другая
  загрузка) — отказ без запроса. `ApiRequest` больше не печатает тело в `Debug`
  (только длину): в нём теперь бывает пароль. Последствия, которые терминал
  называет в `e2ee.resetDone`: собеседники получают `KeyChanged` и должны
  `/trust` или `/verify`; прочие свои устройства подписаны старым ключом и
  становятся неподписанными (их подписывает `/verify <свой логин>` отсюда);
  бэкап хранит старый `crossSigning`, и его ключ восстановления больше не
  восстанавливает подпись (`try_complete_restore` сверяет с каталогом) — нужен
  новый `/backup create`. Проверено вживую: потерянное устройство без бэкапа →
  `/keys reset` (неверный пароль — отказ, верный — новый ключ самоподписи на
  сервере, новое устройство подписано им, потерянное — нет) → у собеседника
  сообщение держится на ⧗ с «у alice изменились ключи» → `/trust` → новое
  устройство читает E2EE-сообщение.
- **Оверлей не слышит открывшую его клавишу** (`ui.js`, найдено на `/keys
  reset`): Blessed отдаёт Enter композеру (команда открывает оверлей), а затем

### 8.8 Доверие на всех устройствах аккаунта (реализовано 2026-11-11, 1.145)

«не проверено». Причина: `peer_identities` — запись хранилища **одного** устройства.

- **Подпись доверия.** `CrossSigning::attest_peer(peer, master)` (`tailchat-crypto`,
  `cross_signing.rs`) подписывает `{login, usage: "peer_verified", peer, key}`
  **ключом самоподписи**. Как в Matrix, но без отдельного user-signing ключа: закрытый
  мастер-ключ выбрасывается при создании (§8.4), а ключ самоподписи есть на каждом
  подписанном устройстве аккаунта. Подписи устройств и доверия разделяет `usage`
  (у `deviceKeys` его нет). `CrossSigningPublic::attested_peer` принимает подпись,
  только если `login` — этот аккаунт, `usage` и подпись **текущего** ключа самоподписи
  верны. Подписи, сделанные до сброса своих ключей, недействительны сами собой.
- **Сервер** (`accounts.js` `e2eeTrust`, `POST /api/e2ee/trust`, журнал `e2ee-trust`):
  хранит `state.e2ee[login].trust = {peer: statement}` (новая заменяет старую,
  ≤ 1000 на аккаунт, ≤ 50 за запрос, всё или ничего). Проверяет только форму:
  `login`/`peer` совпадают с ключом записи, `peer` — друг, не сам; нужна сессия
  с зарегистрированным устройством. `keys/query` отдаёт `peerTrust` **только о самом
  спрашивающем**: кого он сверял — его дело, ни собеседник, ни друзья этого не видят.
  Изменение — `device-list-changed` о себе **только своим сессиям**
  (`hub.trustChanged`), друзьям ничего.
- **Ядро** (`engine/keys.rs`): ответ `keys/query` о себе → `refresh_attested`
  (проверенные подписи, `E2ee.attested`). Собеседник считается сверенным, если
  подписанный ключ равен ключу, который он публикует **сейчас**; если в каталоге его
  нет — то закреплённому здесь. Тогда `PutPeerIdentity{verified: true}`, ожидающая
  смена ключа снимается (как `ConfirmSafetyCode`), а `Event::SafetyCode` перерисовывает
  «Детали». Публикует `post_trust`: устройство, держащее текущий ключ самоподписи,
  подписывает каждую свою проверку, которой нет на сервере, — но только если ключ ещё
  опубликован собеседником, чтобы устаревшая запись не затёрла сверку, сделанную на
  другом устройстве позже. Так одним путём идут новая сверка, перенос сверок, сделанных
  до 1.145, и переподпись после своего сброса ключей. Свой аккаунт ядро переспрашивает
  после регистрации устройства, после сброса и по любому `device-list-changed` о себе.
- **Не делает:** «разверить» нельзя (такого действия нет); неподписанное своё
  устройство сверяет только у себя, пока его не подпишут; APK без ядра не участвует.
- Проверка: `a_peer_attestation_holds_only…` (crypto), `a_verification_made_on_one_device…`
  (два устройства, перезапуск, подделка сервером, сброс ключей у собеседника и у себя),
  `whom an account verified…` (сервер); мутация «не проверять подпись» роняет оба
  Rust-теста.

### 8.9 Одна сверка собеседника (реализовано 2026-11-12, 1.146)

Владелец спросил, почему сверка такая сложная, по сравнению с Signal, Matrix и секретными
чатами Telegram. Ответ — «да. нормально» на два упрощения без смены криптографии:

- **Собеседник сверяется одним способом — кодом безопасности** (как номер безопасности в
  Signal). Живая сверка (SAS) осталась только для своих устройств: только она передаёт
  новому устройству ключ самоподписи. «Сверить» в меню беседы веба открывает «Детали» на
  коде; кнопки «Сверить вживую» в «Деталях» больше нет; `/verify <собеседник>` в
  терминале и вебе показывает код (§8.7). Входящий SAS от старого клиента ядро по-прежнему
  проводит, ответ — тот же `/verify yes|no`.
- **«Не сверено» — спокойное предложение, а не тревога.** Текст в «Деталях» начинается с
  «Необязательно…» и говорит, что достаточно одного раза, цвет приглушённый. Громко — только
  смена ключей собеседника: `data-verified="changed"`, цвет `--danger`, текст
  `safetyKeyChanged` и два выхода прямо там — «Совпадает — отметить сверенным» и «Принять
  новые ключи» (`/trust`). Без второго выхода человек, у которого отправка собеседнику
  стоит до решения, оставался бы без кнопки в самих «Деталях».

Ядро и сервер не менялись. Третье предложение — предлагать при входе на новом устройстве
восстановление из бэкапа (оно уже подписывает устройство) вместо сверки со вторым — отложено.

# tailchat против chat-tails

Сравнение с [bscott/chat-tails](https://github.com/bscott/chat-tails) — 147 звёзд,
Go, MIT. Составлено по README и структуре репозитория на 2026-08-13.

Короткий вывод: **это разные архитектуры под разные задачи, а не конкуренты.**
chat-tails — комната, куда заходят через `netcat`. tailchat — личный мессенджер
между конкретными людьми и их устройствами.

## Топология

```
chat-tails                          tailchat

nc/telnet ─┐                        клиент ◄──────► клиент
nc/telnet ─┼─► сервер в tailnet         (прямое соединение,
nc/telnet ─┘   (tsnet + TS_AUTHKEY)      сервера нет)
```

У них сообщения проходят через центральный узел, который надо где-то держать
запущенным. У нас соединение прямое, и падать нечему — кроме самих собеседников.

## Таблица

| | chat-tails | tailchat |
|---|---|---|
| модель | комната, сервер + клиенты | P2P 1:1, без сервера |
| язык | Go, один бинарник | Node.js |

| присутствие в tailnet | сервер входит как **отдельный узел** через `tsnet` + `TS_AUTHKEY` | ничего не добавляет, использует локальный `tailscaled` |
| авторизация | кто дотянулся до порта, то есть ACL | `tailscale whois` на каждое входящее: только устройства заданного логина |
| участников | много | двое |
| редактирование строки | нет, поток `netcat` | полноценный композер |
| расписки о доставке | нет | `→ / ✓ / ✓✓` с доказательством |
| присутствие | нет | `ACTIVE / IDLE / AWAY` по событиям фокуса |

## Где он сильнее

**Нулевая установка у собеседника.** `nc mychat.ts.net 2323` — и человек в чате.
Это самое весомое их преимущество. Не нужно уговаривать ставить Node, следить за
совпадением версий, разбираться с Termux на Android. Ровно те мучения, которые у
нас случились при подключении второго участника, там отсутствуют по конструкции.

**Групповой чат.** У нас 1:1 заложено в фундамент: rendezvous с арбитражем по
`connId` предполагает ровно два конца. Дёшево это не расширяется.

**Упаковка.** Dockerfile, systemd-юнит, GitHub Actions, `make build-all` под все
платформы. У нас установка — это клон репозитория.

## Где сильнее наш

**Личность собеседника проверяется, а не предполагается.** У них авторизация
сводится к «дотянулся до TCP-порта»: любой узел tailnet может подключиться и
представиться каким угодно именем — `netcat` не спрашивает, кто вы. У нас каждое
входящее соединение проходит `tailscale whois` у локального демона: подключиться
могут только устройства заданного логина, и подделать это через сокет нельзя,
потому что ответ даёт не собеседник, а ваш собственный `tailscaled`.

**Не требует ни ключа, ни лишнего узла.** `TS_AUTHKEY` создаёт в tailnet
отдельную машину, за которой надо следить, и ключ, который надо хранить. Мы
работаем поверх демона, который на устройстве уже есть, и не добавляем ничего.

**Нечего держать запущенным.** Их модель требует живого сервера. У нас оба конца
симметричны: кто запустился — тот и слушает.

**Клиент, а не поток строк.** Участник комнаты получает построчный вывод без
редактирования, расписок, файлов и присутствия. У нас всё это есть, плюс очередь
на время обрыва, звонок собеседнику, история на диске, автодополнение команд и
самообновление.

## Что стоит позаимствовать

1. **`/me <действие>`** — `* Roman машет`. Несколько строк кода, попадает в
   характер проекта. Рекомендую.
2. **Ограничение частоты сообщений.** У нас оно есть только на `/wake`. В 1:1 с
   проверенной личностью флудить особо некому, поэтому необязательно.
3. **Режим `tsnet`.** Настоящий пробел: там, где нет `tailscaled` — в контейнере
   или на чужой машине — наш клиент не запустится вовсе. Но это большая работа, и
   она требует auth-ключа, то есть ломает принцип «ничего не добавляем в tailnet».
   Скорее нет, чем да.

Их `--plain-text` для устаревшего Windows telnet у нас уже закрыт флагом
`--no-theme` и монохромным режимом, включающимся и по `NO_COLOR`.

## Когда что выбирать

- Нужна **комната** и участники не готовы ничего ставить — chat-tails.
- Нужна **переписка с конкретным человеком**, с файлами, расписками и гарантией,
  что пишет именно он, — tailchat.
